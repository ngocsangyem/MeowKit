title: "Autonomous Build"
description: "Build a green-field product with /mk:autobuild: a product-level plan, an optional sprint contract, and a generator and evaluator loop whose scaffolding follows the model."
---

`/mk:autobuild` builds a whole product from a description, such as "build me a kanban app". For a single feature on an existing codebase use `/mk:cook`, and for a bug use `/mk:fix`.

```bash
/mk:autobuild build a kanban board with drag-and-drop
```

The run detects your model, picks how much scaffolding to use, writes a product-level plan for you to agree, builds, and has a separate evaluator grade the running app. A failed grade sends the work back to the generator, up to three rounds.

## Before you start

- Sonnet runs at FULL density, Opus 4.6 and later and Fable at LEAN. Haiku hands the task to `/mk:cook`.
- Density is detected from the `model` field the host sends at session start. If your host does not send it, set `MEOWKIT_MODEL_HINT` (for example `opus-4-6`) or pass `--tier`.
- Set a budget for long runs with `--budget 50`, or `budget.cap: 50` in `.meowkit/config.yaml`.
- Run `mewkit doctor` first to check the install.

## The pipeline

| Step | What happens |
|---|---|
| 0. Tier detection | `mk:scale-routing` picks the density (MINIMAL, FULL or LEAN). The run directory `tasks/autobuild-runs/YYMMDD-HHMM-{slug}/` is created. |
| 1. Plan | `mk:plan-creator --product-level` writes user stories and a design language, with no file paths or class names. You agree the spec before the build starts. |
| 2. Contract | `mk:sprint-contract` turns the stories into acceptance criteria tied to rubrics. Skipped on MINIMAL, and on LEAN when fewer than 5 criteria are expected. |
| 3. Generate | A `developer` subagent builds in subphases (understand, design, implement, verify, handoff) and writes a handoff file. |
| 4. Evaluate | An `evaluator` subagent grades the running build through `mk:evaluate`. |
| 5. Iterate or ship | On PASS the harness asks whether to ship. On WARN or FAIL with rounds left it returns to step 3 with feedback. |
| 6. Run report | The audit trail is written to `run.md`. |

Four roles take part. The planner sets the ambition and leaves the path to the generator, because naming files up front narrows what the generator can find. The generator (the `developer` agent) builds. The evaluator is a separate agent with a fresh context and a skeptic persona. The skill itself orchestrates the loop, the budget and the escalation.

### Generator and evaluator stay separate

They are distinct subagents with isolated contexts. The generator never sees the evaluator's reasoning, and the evaluator never grades its own work. The evaluator re-anchors its skeptic persona before each criterion, because grading gets more lenient the longer it runs.

### Active verification

The evaluator drives the running build through a browser, `curl` or the CLI, and writes screenshots or command output to an `evidence/` directory. A PASS with an empty evidence directory is converted to FAIL by `validate-verdict.sh`. Static analysis alone never produces a verdict.

## Density

| Mode | Model | Planner | Contract | Iteration | Context reset |
|---|---|---|---|---|---|
| MINIMAL | Haiku | Skipped, runs `/mk:cook` | Skipped | Skipped | Skipped |
| FULL | Sonnet, Opus 4.5 and older | Product-level | Required | 1 to 3 rounds | Optional (required on Opus 4.5) |
| LEAN | Opus 4.6 and later, Fable | Product-level | Optional | 0 to 1 rounds | Skipped (auto-compaction) |

Override the detected density with `--tier` or an environment variable:

```bash
/mk:autobuild build a todo app --tier full
export MEOWKIT_AUTOBUILD_MODE=LEAN
```

Density changes how much scaffolding runs, not the quality bar. The plan, the review verdict and the evaluator's active verification apply in every mode. See [Adaptive density](/guide/adaptive-density) for the full matrix.

## The sprint contract

The contract lists testable acceptance criteria (5 to 15, in Given/When/Then form, each with a verification line and a rubric tie-in) before the generator writes code. The `developer` and `evaluator` agents negotiate it in up to two rounds and both sign it. It exists because capable models otherwise substitute features silently.

The developer reads the signed contract before editing source. No hook checks that it did. The contract is a working agreement between the two agents, not an enforced stop.

## Iteration, budget and the ship question

- **Rounds.** The generator and evaluator loop at most 3 times by default (`--max-iter N`). After that, the harness stops and asks you what to do.
- **Budget.** `budget-tracker.sh` warns at $30 and halts the run at $100, unless `--budget` or `budget.cap` sets a different cap. A halted run ends as TIMED_OUT. A run also stops after 6 hours.
- **Shipping.** A verdict is evidence, not a decision. On PASS, or on WARN at the round limit, the harness shows the verdict and evidence and asks whether to ship, iterate with your feedback, or abort. The shipper runs only after you say yes.

| Status | Meaning |
|---|---|
| PASS | The evaluator passed the build |
| WARN | Minor issues, acceptable once you have seen each one |
| FAIL | The evaluator rejected the build |
| ESCALATED | The round limit was reached with a FAIL, or you aborted |
| TIMED_OUT | Budget or time limit reached |

## Optional flags

| Flag | Effect |
|---|---|
| `--tier auto\|minimal\|full\|lean` | Force a density |
| `--max-iter N` | Rounds before escalation (default 3) |
| `--budget N` | Spend cap in USD |
| `--tdd` | Write the TDD sentinel so the developer waits on the tester before each generator round |
| `--advice` | The `athena` agent advises at named checkpoints (at most 5 per run). Its advice is evidence, never an approval |

## What a run leaves behind

| Artifact | Location |
|---|---|
| Product plan | `tasks/plans/{plan-dir}/plan.md` |
| Sprint contract | `tasks/contracts/{date-time}-{slug}-sprint-N.md` (when not skipped) |
| Generator handoff | `tasks/handoff/{slug}-sprint-N.md` |
| Evaluator verdict | `tasks/reviews/{slug}-evalverdict.md` |
| Run report | `tasks/autobuild-runs/YYMMDD-HHMM-{slug}/run.md` |

The run report records the density decision and its source, one section per step, and the budget trail. It is append-only, and a killed run restarts from the `next_step` it records.

## Reading the verdict

The verdict holds a score per rubric, a weighted overall score and a pointer to the evidence behind each grade. Any rubric whose result reaches its hard-fail threshold sets the overall verdict to FAIL, whatever the weighted average is. The default `frontend-app` preset grades `product-depth`, `functionality`, `design-quality` and `originality`. See [Rubric library](/guide/rubric-library).

## When it goes wrong

**Density is FULL but you are on Opus 4.6 or later.** Detection found no `model` field. Set `export MEOWKIT_MODEL_HINT=opus-4-6` and restart, or pass `--tier lean`. The run report shows `Source: auto-fallback` when the fallback fired.

**The run passed the budget.** Lower the cap with `--budget 30`, or shrink the product spec. Total work follows the planner's output more than anything else.

**The evaluator says FAIL and the build looks fine.** Open the evidence directory, which holds output behind every graded criterion. `/mk:elicit` examines one rubric in more depth, and you can recalibrate anchors in `.claude/skills/rubric/rubrics/`.

**The run was interrupted.** Open `run.md` in the run directory and continue from the step named by `next_step`.
