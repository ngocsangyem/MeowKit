`/mk:ship` is Phase 5 of the workflow. It checks the change, makes conventional commits, and opens a PR on a feature branch. It never pushes to main directly.

## Scopes

Bare `/mk:ship` only prepares. Anything that leaves your machine needs an explicit request.

```bash
/mk:ship                    # prepare: inspect, run checks, ask before the local commit
/mk:ship release            # push the branch, create or update the PR
/mk:ship publish            # versioning, changelog and issue actions
/mk:ship release beta       # target the dev branch instead of main
/mk:ship --dry-run          # show the actions, run none of them
```

| Scope | What it does |
|---|---|
| `prepare` (default) | Inspects the selected changes, runs checks, shows the files proposed for staging, and asks before the local commit. No push, PR or version change. |
| `release` | After you ask, pushes the branch and creates or updates the PR. Runs `mk:document-release` before merge so docs land in the same PR. |
| `publish` | After you ask, decides the version and changelog with you and handles issue actions. It never picks a version bump on its own. |

`official` targets the default branch (main or master). `beta` targets the dev branch and appends a prerelease suffix such as `-beta.1` to the version. With neither, a `feature/*`, `hotfix/*` or `fix/*` branch ships as official, a `dev/*` or `beta/*` branch ships as beta, and otherwise the skill asks. `--skip-tests` skips the test step only when you confirm current-session evidence is enough.

## The ship check

On `git commit`, `git push`, `git merge` and `gh pr create|merge`, the `pre-ship` hook runs lint on the changed files, the tests related to them and a type-check. It refuses the command when one fails. This is the one control enforced at ship time. A missing plan or review verdict blocks nothing, and `mk:ship` says so when it sees either missing. See [Enforcement and security](/core-concepts/enforcement).

## What the pipeline does

1. Pre-flight: detect the base branch, check you are not on it, and read the review status.
2. Merge the base branch and run the tests, separating failures you caused from ones already there.
3. Audit test coverage and the plan against the diff.
4. Pre-landing review. Adversarial review belongs to `mk:review`, and ship does not repeat it.
5. Version bump and changelog, when you asked for `publish`.
6. Commit in conventional format, with the scope and description taken from the plan.
7. Push and PR creation on `release`.
8. Verify CI and document rollback steps in the PR body.

The final summary reports one deploy classification with a line of evidence: `deployed`, `PR-only` or `not-applicable`.

## Stops

The pipeline stops on any of these:

- You are already on the target branch.
- Merge conflicts it cannot resolve.
- Test failures on your branch.
- Coverage below the threshold.
- Plan gaps.

Critical review findings are put to you one at a time. Pre-existing test failures are reported, and it asks whether to go on.

## Hotfixes

```bash
/mk:fix "critical payment bug" --quick
/mk:ship
```

A hotfix still gets a review verdict and the ship check. Record the reason in the PR description if you skip a non-critical step.

## Jira tickets

If the review verdict lists `jira_tickets`, `mk:ship` offers three optional actions before it continues: post the verdict summary to the ticket, move the ticket to Done, and confirm each business acceptance criterion. Each one asks first, and each is skipped without cost when Jira is offline.

## Memory

Before you ship, ask for the non-derivable decisions and corrections to be written down. Each is one entry in `.meowkit/memory/`, written with `mewkit note`:

```md
## Connection pool, not per-request connection   <!-- 2026-11-01 -->
Why: load testing showed 3x throughput; per-request exhausted the pool under burst
Apply when: adding any new DB-backed endpoint to this service
Source: PR #318
```

The store is committed, so the entry ships in the same PR and is reviewed with the code.

## When it goes wrong

| What you see | Why | What to do |
|---|---|---|
| The ship check refuses the command | Tests, lint or types are failing | Fix them, then retry |
| Merge conflicts | The base branch moved | Resolve them, then re-run |
| CI fails but passed locally | The CI environment differs (Node version, env vars) | Read the CI logs and fix the difference |
| `gh` not found | GitHub CLI is not installed | Install `gh`, or push and open the PR in a browser |

## Don't use /mk:ship for

- Features still in development. Finish the review first.
- Force pushes. MeowKit force-pushes only when you ask for it.
