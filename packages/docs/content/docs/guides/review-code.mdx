`/mk:review` runs a multi-pass review of a change and writes one verdict. It is Phase 4 of the workflow and also a standalone command.

```bash
/mk:review              # current branch diff against the base branch
/mk:review #42          # a pull request
/mk:review --pending    # staged and unstaged changes
/mk:review abc1234      # a single commit
```

For a PR, `mk:review` first runs `mewkit review prepare`. That creates a detached review worktree, captures one hash-pinned diff with the PR metadata and CI status, and writes an impact map. PR text is stored as data and never followed as instructions.

## How the review runs

The first step gathers the diff, plan and acceptance criteria, then sets the review scope.

| Scope | When | Who reviews |
|---|---|---|
| minimal | 3 files or fewer, 50 lines or fewer, no security files, not a high-complexity domain | Blind Hunter only |
| full | anything larger | All three base reviewers, then adversarial personas |

The three base reviewers run in parallel so they do not anchor on each other:

1. **Blind Hunter** sees only the diff, with no plan or spec.
2. **Edge Case Hunter** traces boundaries, null paths and every branch.
3. **Criteria Auditor** maps each acceptance criterion in the plan to the implementation.

On a full-scope review, persona passes follow. They receive the diff and the base findings and go deeper: Security Adversary, Failure Mode Analyst, and, for high-complexity domains, Assumption Destroyer and Scope Complexity Critic. If all reviewers find nothing, the triage step re-analyzes once with a "look harder" prompt.

Triage sorts findings into `current-change` and `incidental`, then the verdict step checks the code for stubs, orphaned exports and unwired code.

## The verdict

| Dimension | PASS | WARN | FAIL |
|---|---|---|---|
| Correctness | No critical or major bugs | Minor bugs only | Any critical bug |
| Maintainability | Clean, follows conventions | Style issues | Unreadable or breaks the architecture |
| Performance | No regressions | Potential issues flagged | Proven regression |
| Security | No findings | Minor notes | Any critical issue |
| Coverage | Every criterion covered and tested | Partial coverage | A criterion is not implemented |

Any FAIL makes the overall verdict FAIL, and an average never hides it. All PASS is ready to ship. A mix of PASS and WARN is ready once you have seen each WARN. The verdict is written under `tasks/reviews/`.

A FAIL is advice: the change is not ready, and the findings say what to fix. No hook blocks a commit on it. In a PR review prepared with `mewkit review prepare`, subagent reads are attested without hook corroboration, so approval is capped at `PASS_WITH_RISK` and the verdict says so.

If the diff changes existing behavior, the verdict carries a `Side Effects Detected` line. The change is not ready to ship until you have chosen a recovery option, which is recorded on the verdict.

## Optional follow-ups

```bash
/mk:cook "feature" --verify   # light browser check after review
/mk:cook "feature" --strict   # full evaluator with rubric grading
/mk:elicit                    # second pass on WARN dimensions
```

`--verify` checks that pages load without console errors. `--strict` clicks through the app and grades it against rubrics. `/mk:elicit` pushes on findings with structured methods such as pre-mortem and red team.

For changes of three or more files, run `/mk:scout` first so reviewers start from the affected dependents.

## Don't use /mk:review for

- Bug investigation. Use `/mk:fix`.
- A whole-repository security audit. Use `/mk:cso`. The security dimension here covers the diff only.
- Architecture decisions. Use `/mk:party`.
