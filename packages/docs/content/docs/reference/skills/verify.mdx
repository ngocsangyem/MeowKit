## What it does

`mk:verify` is the Phase 3.6 step between Build and Review. It runs build, lint, type-check, tests and coverage in sequence, stops on the first failure and prints one PASS or FAIL report with a result per step. A PASS hands off to `mk:review`. A FAIL goes back to the developer, who fixes it and runs verify again. It also runs as the `mk:ship` pre-flight and on request ("is everything green?").

## When not to use it

For a lint and validation sweep as a standalone job, use `mk:lint-and-validate`.

## Usage

| Flag | Effect |
|---|---|
| `--full` | Checks the whole project, including coverage. Use for releases and CI. |
| `--coverage-threshold N` | Sets the coverage threshold to N percent. |
| `--skip-build` | Skips the build step. |
| `--skip-coverage` | Skips coverage. |

```
/mk:verify
/mk:verify --full --coverage-threshold 90
```

## Scope

By default verify checks only what changed: files committed since the base branch, staged, unstaged and untracked. The ship check (`pre-ship`) runs later on commit, push and merge.

| Step | Default scope |
|---|---|
| Build | Whole program |
| Lint | Changed files |
| Type-check | Whole program |
| Tests | Tests related to the changed files |
| Coverage | Skipped, reported as `SCOPED` |

Verify runs the whole project when git is unavailable or nothing changed. It also escalates to `--full` when the changes touch build, lint, type or test config, dependency files, lockfiles or CI workflows, and when the changes are only deletions or renames.

## Project detection

The first marker file found picks the commands. If several exist, the most specific wins. With none, the skill asks which build and test commands to use. `references/project-detection.md` has the details and the scoped command for each language.

| Marker | Build | Lint | Type-check | Test |
|---|---|---|---|---|
| `package.json` | `npm run build` | `npm run lint` | `npm run typecheck` or `tsc --noEmit` | `npm test` |
| `pyproject.toml` | `python -m build` | `ruff check .` or `flake8` | `mypy .` | `pytest` |
| `go.mod` | `go build ./...` | `golangci-lint run` | part of build | `go test ./...` |
| `Gemfile` | `bundle exec rake build` | `rubocop` | none | `bundle exec rspec` |
| `Cargo.toml` | `cargo build` | `cargo clippy` | part of build | `cargo test` |

## Coverage threshold

The threshold comes from project config (`.nycrc`, `jest.config`, `pyproject.toml`), then falls back to 80 percent, and `--coverage-threshold` overrides both.

## Output

```
## Verification Report
- Build:      PASS
- Lint:       PASS (3 changed files, 0 errors)
- Type-check: PASS
- Tests:      PASS (related to 3 changed files, 18 passed)
- Coverage:   SCOPED (run with --full for global coverage)
**Overall: PASS**
```

After a failure the remaining steps are listed as `SKIPPED`.

## Gotchas

- For JS and TS, check `pnpm-lock.yaml`, `yarn.lock` or `bun.lockb` before assuming npm.
- In a monorepo with several `package.json` files, ask which workspace to verify or run from the root.
- Go and Rust type-checking is part of the build.
- Re-run flaky tests once before reporting FAIL.
