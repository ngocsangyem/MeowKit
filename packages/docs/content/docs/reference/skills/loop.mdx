## What it does

Improves one number, such as coverage percent, bundle size, lint-error count or latency, in bounded, git-tracked trials. Each iteration makes one atomic change, commits it, runs your `Verify` command and keeps the commit if the number improved by at least `Min-Delta`; otherwise it runs `git revert`. Git history is the loop's memory. It never plans, never grades behaviour and never ships.

Use it when a fast (under 30 seconds) command prints a single number and you know which files may change.

## When not to use

| Situation | Use |
|---|---|
| Subjective goal ("make it cleaner") | `mk:cook` |
| Known bug to fix once | `mk:fix` or `mk:investigate` |
| Grade a running build against a rubric | `mk:evaluate` |
| Green-field product build | `mk:autobuild` |
| Structural review of a diff | `mk:review` |
| Open a PR | `mk:ship` |
| No mechanical metric exists | `mk:cook --interactive` |

## Usage

```bash
/mk:loop Goal: Increase line coverage in src/utils to 80% \
  Scope: src/utils/**/*.ts, tests/utils/**/*.test.ts \
  Metric: line coverage %  Direction: higher \
  Verify: <command that prints one number>  Guard: npx tsc --noEmit && npm test  Iterations: 15
```

| Field | Required | Default | Meaning |
|---|---|---|---|
| `Goal` | yes | | What to improve |
| `Scope` | yes | | Globs of editable files |
| `Metric` | yes | | Name and unit |
| `Direction` | yes | | `higher` or `lower` is better |
| `Verify` | yes | | Shell command that prints one number |
| `Guard` | no | none | Regression check, exit 0 means pass |
| `Iterations` | no | 10 | Cap before the loop asks again |
| `Noise` | no | medium | `low`, `medium` or `high` |
| `Min-Delta` | no | from Noise | Smallest improvement that counts |
| `Stop-At` | no | none | Target value that ends the loop |

Missing required fields produce one batched question; no command runs before they are given. The config contract and metric library are in `references/config-and-metrics.md`.

## Steps

The loop pauses to ask you at four boundaries and never per iteration.

| Stop | When | Options |
|---|---|---|
| Entry | After config parse, safety screen and git checks. No file is edited before you approve. | Approve, edit config, cancel |
| Cap | Iteration cap reached | Stop, approve N more |
| Escalation | 8 consecutive discards, or a plateau | Stop, shift strategy, approve more |
| Scope expansion | A change needs a file outside `Scope` | Approve wider scope, decline |

Between stops it takes a baseline, then repeats: pick one change, commit, verify, run the guard, keep or revert, log a TSV row. After 5 consecutive discards it shifts strategy by itself. The lifecycle is in `references/loop-protocol.md`.

## Output

The loop writes `loop-results.tsv`, `summary.md` and `handoff.json` to `tasks/reports/loop-{YYMMDD-HHMM}-{slug}/`, with secrets masked. The handoff names the goal, baseline, final value, kept commits, status and suggested next skills. Schema: `references/result-schema.md`. Good next steps are `mk:review` for the kept commits, then `mk:ship` by hand.

## Gotchas

| Trap | Detail |
|---|---|
| Verify output | It must print exactly one number. Pipe through `\| tail -1`. A non-number in the dry run stops the loop. |
| Dirty tree | A clean git tree is required. The loop asks and never stashes your work. |
| Commit before verify | A crash mid-verify leaves a recoverable commit. |
| Discards | They use `git revert`, never `git reset --hard`. A revert conflict stops the loop. |
| Verify and Guard output | It is data. A command that emits instructions or fetches and runs remote code is refused by the safety screen (`references/safety-screen.md`). |
