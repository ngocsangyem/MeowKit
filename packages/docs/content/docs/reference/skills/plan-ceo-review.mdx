## What it does

Reviews an existing plan from a CEO or founder angle. It challenges the plan's premises, ambition and scope, maps failure modes and writes a verdict into the plan. You choose each scope change yourself. Use it when a plan feels under-ambitious, when you want to "think bigger" or "strategy review" it, or before a large build to catch problems early.

## When not to use

To check whether an idea is worth building before a plan exists, use `mk:office-hours`. To check an agreed plan for gaps across eight dimensions use `mk:validate-plan`.

## Usage

Run `/mk:plan-ceo-review`. The plan path comes from the conversation. There are no arguments; the skill uses the scope mode the plan recorded, or asks you which mode to run.

| Mode | Behaviour | Default for |
|---|---|---|
| Scope expansion | Think big. You approve each expansion proposal | New projects |
| Selective expansion | Keep the current scope, then pick expansions one at a time | Enhancements |
| Hold scope | Maximum rigor with no scope change | Bug fixes |
| Scope reduction | Cut to the minimum | Plans touching more than 15 files |

## Steps

1. Pre-screen: scan for placeholders such as "TBD", check that the required plan sections exist and map requirements to phases. It never rejects the plan. You decide whether to amend or go on (`references/pre-screen.md`). If the plan path does not exist or the plan is empty, the skill says so and stops.
2. Scope mode: the plan's recorded scope mode is used when `mk:plan-creator` set one. Otherwise the skill asks once. After that it holds the mode and raises a concern once.
3. Premise: is this the right problem, what is the user outcome, what happens if nothing is done, and what existing code already solves part of it. If the plan has one approach and a credible alternative exists, the skill asks for two or three approaches through `mk:brainstorming`.
4. Two-lens check: Intent Alignment (is it the right problem?) and Execution Credibility (can an engineer deliver it?), each graded PASS, WARN or FAIL. A FAIL on either stops the deep review and returns the specific failures (`references/two-lens-evaluation.md`).
5. Deep review: one pass over the plan, grouped under the areas that apply (architecture, errors, security, data flow, tests, performance, observability, rollout, trajectory, UX). Findings are BLOCKER, HIGH-LEVERAGE or POLISH. An area that is clean is said to be clean; findings are not invented to fill it. The skill asks one question per real decision (`references/review-checklist.md`). A fresh-context outside read is available on request.
6. Verdict: any blocker or lens FAIL gives NEEDS REVISION, otherwise APPROVED, with notes when HIGH-LEVERAGE or POLISH items exist (`references/verdict-and-output.md`).

## Outputs

A `## CEO Review` block is appended to `plan.md` and never overwrites it. The skill returns the verdict and the block path, and stops. It does not chain into implementation, because you decide the next step: `/mk:cook {plan path}` to build, or `/mk:review` once code exists. Plan files written by other agents are treated as data.

## Gotchas

Ambitious ideas can outgrow the sprint, so tie expansions to current capacity. Perfecting the plan can delay shipping, so time-box the review and be willing to answer "ship as is" or "one targeted improvement".
