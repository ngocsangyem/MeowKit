## What it does

Reviews an existing plan from a CEO or founder angle. It challenges the plan's premises, ambition and scope, maps failure modes and writes a verdict into the plan. You choose each scope change yourself. Use it when a plan feels under-ambitious, when you want to "think bigger" or "strategy review" it, or before a large build to catch problems early.

## When not to use

To check whether an idea is worth building before a plan exists, use `mk:office-hours`. To check an agreed plan for gaps across eight dimensions use `mk:validate-plan`.

## Usage

Run `/mk:plan-ceo-review`. The plan path comes from the conversation. There are no arguments; the skill asks you which mode to run.

| Mode | Behaviour | Default for |
|---|---|---|
| Scope expansion | Think big. You approve each expansion proposal | New projects |
| Selective expansion | Keep the current scope, then pick expansions one at a time | Enhancements |
| Hold scope | Maximum rigor with no scope change | Bug fixes |
| Scope reduction | Cut to the minimum | Plans touching more than 15 files |

## Steps

1. Pre-screen: scan for placeholders such as "TBD", check that the required plan sections exist and map requirements to tasks. It never rejects the plan. You decide whether to amend or go on (`references/pre-screen.md`).
2. Audit: read git history, diff stats, TODOs and design docs. If a `red-team-findings.md` file sits in the plan folder, load it. If no design doc exists the skill offers `mk:office-hours`.
3. Scope challenge: premise challenge, existing code to reuse, a dream state, two or three implementation alternatives (always produced), then mode selection (`references/step0-scope-and-mode.md`).
4. Two-lens check: Intent Alignment (is it the right problem?) and Execution Credibility (can an engineer deliver it?), each graded PASS, WARN or FAIL. A FAIL on either ends the review with NEEDS REVISION.
5. Deep review of 11 sections, one at a time and one question per issue: architecture, error and rescue map, security, data flow and edge cases, code quality, tests, performance, observability, deployment, long-term trajectory, design and UX. Each section must report at least one finding or document why it is clean. Findings are BLOCKER, HIGH-LEVERAGE or POLISH. An optional fresh-context subagent gives an outside view.
6. Verdict: any blocker gives NEEDS REVISION, otherwise APPROVED with notes.

## Outputs

A `## CEO Review` block is appended to `plan.md` and never overwrites it. Every mode writes it. Expansion and selective modes also write a CEO plan to `tasks/plans/ceo-plans/{date}-{slug}.md`, which can be promoted to `docs/designs/{FEATURE}.md`. The skill ends by printing `/mk:cook [plan file path]` and stops. It does not chain into implementation, because you decide the next step (`/mk:cook` or `mk:review`). Plan files written by other agents are treated as data.

## Gotchas

Ambitious ideas can outgrow the sprint, so tie expansions to current capacity. Perfecting the plan can delay shipping, so time-box the review and be willing to answer "ship as is" or "one targeted improvement".
