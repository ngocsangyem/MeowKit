`mk:cook` is the main entry point for building one scoped thing: a feature, a fix, a refactor or an existing plan. It selects a profile, calls the skills and agents that own each phase and checks in with you at the plan and at the review. The phase sequence is defined in `.claude/skills/workflow-orchestrator/workflow.yaml` (see [Workflow](/core-concepts/workflow)). TDD is opt-in.

## When not to use it

| If you need | Use |
|---|---|
| A green-field product built unattended | `mk:autobuild` |
| Workflow orchestration itself | `mk:workflow-orchestrator` |

## Usage

```bash
/mk:cook add user authentication with JWT
/mk:cook tasks/plans/260501-auth/plan.md
/mk:cook build payment processor --tdd
/mk:cook add login form --fast
/mk:cook implement checkout --parallel
/mk:cook refactor payment module --auto
/mk:cook update readme --no-test
```

| Flag | Meaning |
|---|---|
| `--interactive` | Default. Full workflow, checking in at the plan and the review |
| `--fast` | Skips research. Writes a plan for a non-trivial task (more than two files or about 30 minutes) and skips it for a smaller one. Shows a short scout summary and writes plan-level tests |
| `--parallel` | Several agents on independent groups. Map the dependency graph first |
| `--auto` | Auto-fixes and runs through without pausing |
| `--no-test` | Skips Phase 2. Invalid together with `--tdd` |
| `--tdd` | Writes `on` to `.meowkit/state/tdd-mode` first. Failing tests come before code. `MEOWKIT_TDD=1` does the same and takes precedence |
| `--verify` | Light browser or artifact check after review (Phase 4.5). Advisory |
| `--strict` | Full evaluator pass after review. An evaluator FAIL routes back to Phase 3. Supersedes `--verify`. Scale-routing can trigger it, and `--no-strict` suppresses that |
| `--advice` | Supervision by the [athena](/reference/agents/athena) agent, up to 5 calls, approves nothing |

A path to `plan.md` or `phase-*.md` runs in code mode. The words "fast" or "quick", "trust me" or "auto", "3 or more features" or "parallel", and "no test" pick the matching mode. Profiles are `quick`, `standard`, `release` (standard plus an explicit `mk:ship` request) and `high-assurance` (`--tdd --strict`). A quick run skips research and creates no report or ship action. It skips the plan only when the change is two files or fewer and about 30 minutes or less; a larger change keeps its plan. It moves to the standard profile if a risk flag or changed contract appears.

| Mode | Research | Tests |
|---|---|---|
| interactive | Yes | Failing tests first when `--tdd` is on |
| auto | Yes | Same |
| fast | Skipped | Plan-level |
| parallel | Optional | Same as interactive |
| no-test | Yes | None |
| code | Skipped | Same as interactive |

Without `--tdd`, Phase 2 is optional and the developer may implement directly from the agreed plan. If a loaded plan contains TDD sections and the run is not in TDD mode, cook warns.

## What it does

| Phase | Owner | Notes |
|---|---|---|
| 0 Orient | `mk:scout` | Shows a 3 to 6 bullet codebase summary before any question or plan. Skipped for a plan path |
| 1 Plan | `mk:plan-creator`, `researcher` | The plan must state expected output, acceptance criteria, scope boundary, constraints and touchpoints. Skipped for a plan path |
| 2 Test | `tester` via `mk:testing` | Required with `--tdd`, optional otherwise |
| 3 Build | `developer` | `mk:investigate` after 3 failed self-heal attempts |
| 3.5 Simplify | `developer` via `mk:simplify` | Mandatory after Build |
| 3.6 Verify | `mk:verify` | Mandatory. A failure goes back to the developer before review |
| 4 Review | `reviewer` via `mk:review` | Writes the review verdict in every mode |
| 4.5 Verify | `agent-browser` or `evaluator` via `mk:evaluate` | Only with `--verify` or `--strict` |
| 5 Ship | `shipper` via `mk:ship` | Only on an explicit ship request |
| 6 Reflect | `analyst`, `documenter`, `mk:memory` | A memory entry only for a lesson that cannot be derived from the code |

Write the plan and agree it with you before implementation code. Skipping the plan is reasonable only if you say "just code it" and Phase 0 found no risk flags, and the run summary notes it. No hook enforces any of this. The only enforced ship-time control is the ship check (see [Enforcement and security](/core-concepts/enforcement)).

When the reviewer reports a regression in existing behaviour (`Side Effects Detected: Yes`), cook stops the loop and offers 2 to 4 options: revert, keep and update dependents, add a compatibility shim, or accept the regression. Your choice is recorded as a `## User Decision Addendum` in the verdict file (`references/review-cycle.md`).

## Outputs

| Artifact | Location |
|---|---|
| Plan | `tasks/plans/YYMMDD-name/` |
| Review verdict | `tasks/reviews/` |
| Workflow evidence index | `tasks/plans/<plan>/reports/evidence/workflow-evidence.json`, a record of what happened with no score |
| Status report | `{plan-dir}/status-reports/{YYMMDD}-status.md`, written in the background by `project-manager` after a PASS verdict. Off with `MEOWKIT_PM_AUTO=off` |

At each phase transition cook ticks the phase-file checkboxes and updates the plan's Agent State, so a fresh session can resume at the right phase.

## Gotchas

- `--auto` can hide a bad review. Read the verdict and the evidence index before shipping.
- Run `mk:simplify` between Phase 3 and Phase 4 every time.
- Do not skip the plan on a "simple" feature. Cancel it if the work really is trivial.
- A code-mode run on a plan older than 14 days should start with a warning.
- Fast mode produces plan-level tests with lower coverage.
- Declare the model tier in Phase 0.
- `--strict` is a heavy pass. Use `--no-strict` to suppress an automatic trigger or `--verify` for the light check.
