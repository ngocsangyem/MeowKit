`mk:development` is a set of reference guides for implementation: code patterns per stack, TDD rules that apply only in TDD mode, and a loader that decides which domain references to read. It supports Phase 2 (Test) and Phase 3 (Build) and is what the `developer` agent reaches for when it needs stack-specific patterns. Use it when coding outside a phase pipeline.

## When not to use it

To run a whole feature through the phases, use `mk:cook`. For quality standards on code you are writing, add `mk:clean-code` alongside: patterns define structure, clean-code enforces quality.

## TDD

TDD is opt-in. The default skips RED-phase enforcement, which suits prototypes and exploration. Turn it on with `--tdd` or `MEOWKIT_TDD=1` for production work. `references/tdd-enforcement.md` applies only then.

| Rule | Content |
|---|---|
| 1 | No implementation code until failing tests exist |
| 2 | Capture the failing output to prove the test runs and fails for the right reason |
| 3 | The whole suite must pass after implementation, not only the new tests |
| 4 | After 3 failed fix attempts, escalate to a person with all outputs |
| 5 | A valid failing test runs to completion, asserts the expected behaviour and fails because it is not yet implemented. Syntax errors, import errors and skipped tests do not count |

Stack patterns in `code-patterns.md`:

| Stack | Patterns |
|---|---|
| NestJS | Module, controller, service and DTO split. Guards on every protected controller. `ValidationPipe` on input. DTOs with validator decorators and no `any` |
| Vue 3 | `<script setup lang="ts">`, Pinia stores in setup style, `useX()` composables only for reusable logic |
| Swift | MVVM with an `ObservableObject` per screen, `async throws` for I/O, protocols for service dependencies |
| All | No `any` (use `unknown` and narrow), explicit return types on public APIs, no magic strings, prefer immutability, one concern per file |

## Skill loader

The loader looks at the files a task touches and loads only the matching references, never everything at once. With several domains (NestJS and Vue in one feature) it loads each. If unsure which domain applies, it asks.

| Detected | Loads |
|---|---|
| NestJS (`.ts` with decorators, `modules/` directories) | NestJS patterns, `review/references/adversarial-review.md`, `testing/references/red-green-refactor.md`, `document-release/references/general-documentation.md` |
| Vue (`.vue` files, `vue` or `pinia` imports) | Vue 3 patterns, `testing/references/visual-qa.md`, `red-green-refactor.md` |
| Swift (`.swift`, `.xcodeproj`) | Swift patterns, `red-green-refactor.md` |
| Database (migrations, `.sql`, Supabase) | `plan-creator/references/adr-generation.md` |
| Planning or architecture | `plan-creator/references/scope-challenge.md`, `adr-generation.md` |
| Deploy, PR, release, rollback | `ship/SKILL.md` |

`tdd-enforcement.md` is listed as always loaded, and its rules apply only in TDD mode.

## Gotchas

- Strict red-green slows exploratory prototyping. Leave TDD off for prototypes.
- Generated files (migrations, schemas) exceed the 200-line guideline by design. Exempt them in the plan's constraints.
