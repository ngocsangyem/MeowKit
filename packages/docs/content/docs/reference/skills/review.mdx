## What it does

`mk:review` is the Phase 4 review. Base reviewers read the diff from different angles, adversarial persona passes challenge their findings on larger diffs, and the skill writes a verdict with five dimensions: Correctness, Maintainability, Performance, Security and Coverage. The review only reports: it does not edit code unless you pass `--fix`. The verdict is advice. Nothing blocks a commit on it; the ship check (lint, related tests, type-check) is the only control that runs at ship time.

## When not to use it

| Need | Use |
|---|---|
| Behavioural check against a running build | `mk:evaluate` |
| Shrinking freshly written code | `mk:simplify` |
| Whole-repo security audit (infrastructure, supply chain, secrets) | `mk:cso` |
| Quick checklist review of a GitHub PR | `mk:review-pr` |

For changes that touch three or more files, run `mk:scout` first so reviewers know the cross-file risks.

## Usage

| Input | Reviews |
|---|---|
| (no args) | The current branch diff against the base branch |
| `--pending` | Staged and unstaged changes |
| `#123` or a PR URL | The PR, prepared with `mewkit review prepare` in an isolated worktree with a pinned diff and an impact map |
| `abc1234` (7 or more hex characters) | One commit |
| `--fix` | With any mode: after the verdict, applies the mechanical AUTO-FIX findings (`references/fix-first-review.md`). Everything else still waits for you |
| `--iterative` | Three-pass review for payments, auth and other high-stakes code |

```bash
/mk:review #42
/mk:review --pending
/mk:review --fix
```

Without `--fix`, fixes go through `mk:fix`.

## Steps

1. `step-01-gather-context` loads the diff, plan and acceptance criteria, and sets the scope: `minimal` (3 files or fewer, 50 lines or fewer, no security files, domain not high) or `full`.
2. `step-02-parallel-review` runs the base reviewers. Minimal scope runs the Blind Hunter only. Full scope adds the Edge Case Hunter and the Criteria Auditor in parallel.
3. `step-02b-persona-passes` (full scope only) runs the Security Adversary and Failure Mode Analyst, plus the Assumption Destroyer and Scope Complexity Critic on high-domain changes. They receive the diff and a summary of the base findings.
4. `step-03-triage` marks each finding `current-change` or `incidental`, removes duplicates and drops any finding without a `file:line`. No finding is a valid result, and a reviewer is never re-run to find one.
5. `step-03b-whole-plan-sweep` looks for cross-file drift when an active plan exists, read from `active-plan.json`.
6. `step-04-verdict` writes the verdict and, in full scope, checks artifacts at four levels: exists, substantive (no stubs or empty catch blocks), wired (each new export has a consumer) and data flowing.

In PR mode, step 03 runs `mewkit review coverage` and stops on any gap. Subagent reads are recorded as attested, which caps the result below Approve.

## Verdict

| Dimension | PASS | WARN | FAIL |
|---|---|---|---|
| Correctness | No critical or major bugs | Minor bugs only | Any critical bug |
| Maintainability | Clean, follows conventions | Style issues | Unreadable or violates the architecture |
| Performance | No regressions | Potential issues flagged | Proven regression |
| Security | No findings | Minor notes | Any critical issue |
| Coverage | All criteria covered and tested | Partial coverage | Missing implementation |

Any FAIL makes the verdict FAIL, all PASS makes it PASS, and a PASS/WARN mix is WARN.

When the diff breaks existing behaviour, the verdict adds `Side Effects Detected: Yes` with one bullet per effect. The user's chosen recovery option is appended as a `## User Decision Addendum`. A verdict without that line means nothing was detected.

Each verdict names the commit it reviewed (`Reviewed commit:` in the markdown, `reviewed_commit` and `reviewed_dirty` in the JSON beside it). [mk:ship](/reference/skills/ship) compares it with the HEAD it ships and calls the verdict stale when code, test or build files changed after the review.

## Outputs

The verdict goes to `tasks/reviews/`. PR mode also writes `tasks/reviews/<session>/impact-map.json`. The skill appends a lesson to `.meowkit/memory/gotchas.md` with `mewkit note gotchas` only when the lesson cannot be derived from the code or git history.

## After the verdict

`mk:elicit` can re-examine findings with a pre-mortem, inversion, red team, socratic or first-principles lens. For a WARN with security findings it suggests red team, and for a WARN with coverage gaps it suggests pre-mortem.

## Gotchas

- Read the surrounding file, not only the diff hunks, or an unstated invariant can break unnoticed.
- Rank findings security, then correctness, then performance, then style.
- The design checklist runs only on frontend diffs and matches source patterns. It does not render the UI.
