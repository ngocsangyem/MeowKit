## What it does

`mk:scout` splits the project into segments, searches them in parallel with read-only Explore subagents and returns one consolidated report. Use it before planning a feature that spans several directories, when you need to locate files, or before a review of a diff that touches three or more files. It runs in Phase 0 (Orient) and Phase 1 (Plan), and the orchestrator invokes it before the planner on complex tasks.

## When not to use it

Scout searches the local repository only. For library and API documentation use `mk:docs-finder`.

## Usage

```
/mk:scout authentication
/mk:scout database migrations
```

The argument is the search target. There are no flags.

## Steps

1. Parse the prompt into search targets.
2. Compute the scale with the formula in `references/scouting-strategy.md`.
3. Apply the search scope: Tier 1 directories always, Tier 2 when relevant, Tier 3 never (`references/search-scope.md`).
4. Give each Explore agent a distinct set of directories.
5. Spawn all agents in one message so they run in parallel.
6. Merge results, remove duplicates and note gaps and timeouts.
7. Fill the report template and hand off to the next agent (`references/report-and-handoff.md`).

## Limits

| Limit | Value |
|---|---|
| Writes | None. Scout never modifies files. |
| Parallel agents | 6 at most |
| Timeout per agent | 3 minutes. Non-responders are skipped, not retried. |
| Secrets | `.env`, credentials and SSH keys are never read. |

The 6-agent cap differs from the 3-agent cap in `cook`'s parallel execution rules because that cap covers agents that write files. Scout agents only read, so they cannot conflict.

## Gotchas

- A subagent can return truncated output when its context fills. Set file count limits per subagent and merge with deduplication.
- Default globs skip dotfiles. Include them explicitly when scanning config directories.
