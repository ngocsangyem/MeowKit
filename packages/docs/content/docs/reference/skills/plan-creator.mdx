## What it does

Writes the multi-file implementation plan before you build: an overview `plan.md` of at most 80 lines plus one `phase-XX-*.md` file per phase, saved under `tasks/plans/YYMMDD-name/`. The flow is classify, inspect, capture missing decisions, draft, validate and present the plan to you. Reach for it when a task is non-trivial (more than 2 files, more than an hour, or an architectural decision), when you give it two or more upstream reports, or when a green-field product build needs a spec. Planning is a practice here: the skill asks you to agree the plan, but no hook blocks an edit if you skip it.

## When not to use

| Situation | Use |
|---|---|
| Audit a plan that exists | `mk:validate-plan` |
| Explore options before the approach is chosen | `mk:brainstorming` |
| Trivial or single-file change, or a simple fix | Skip planning; `mk:fix` |
| Build the plan | `mk:cook` or `mk:autobuild` |

## Usage

```bash
/mk:plan-creator "add OAuth login" [--fast | --hard | --deep | --parallel | --two | --product-level | --spike --timebox 2d] [--tdd] [--advice]
/mk:plan-creator archive
/mk:plan-creator red-team tasks/plans/<plan>
/mk:plan-creator validate tasks/plans/<plan>
```

| Flag | Mode and output |
|---|---|
| none | Picks a mode from the scope |
| `--fast` | `plan.md` only, no research |
| `--hard` | Two researchers, `plan.md` and phase files, full validation interview |
| `--deep` | Hard plus a bounded phase map (file inventory, test gaps, interfaces, dependencies) |
| `--parallel` | Hard plus an ownership matrix |
| `--two` | Two approach files and a trade-off matrix |
| `--product-level` | A product spec in `plan.md` only (user stories, features, design language); `--no-design` and `--no-scout` trim it |
| `--spike` | Time-boxed investigation. Requires `--timebox <duration>` and is incompatible with `--product-level` and autobuild FULL density |
| `--tdd` | Adds tests-first sections and carries `--tdd` into the cook handoff |
| `--advice` | Up to four strategic checkpoints from the `athena` agent. It never writes or settles the plan |

The long explanation of each mode is in [Plan creator modes and flags](/core-concepts/plan-creator-modes-and-flags). The `archive`, `red-team` and `validate` subcommands route to `references/archive-workflow.md`, `red-team-standalone.md` and `validate-standalone.md`. A hard or deep plan still runs its own red team and validation interview.

## Steps

Before drafting, the skill can state the expected output, acceptance criteria, scope boundary, constraints and touchpoints in concrete sentences. Each clarifying question cites file paths found by scout.

| Step | What happens |
|---|---|
| 0 | Scope challenge: exit for trivial, fast for simple, hard or deep for complex |
| 0 (cont.) | If two or more upstream artifacts exist, consolidate them into an intake packet |
| 1 | Create the plan directory, research unknowns and scout the codebase (hard family) |
| 3 | Draft `plan.md` and the phase files |
| 4 | Semantic and structural checks |
| 5 | Red team with up to four personas, recorded in `red-team-findings.md` |
| 6 | Validation interview of three to five critical questions, with answers written back |
| 7 | Present the plan: Looks right, Modify or Reject |
| 8 | Turn phase checkboxes into session tasks |
| 9 | Ask what next (`cook`, `validate`, `red-team`, `autobuild` or `end`), write `handoff.next` into `plan.md` and stop |

After steps 5 and 6 a whole-plan consistency sweep stages edits and applies them only once you resolve any contradictions (`references/whole-plan-sweep.md`). If the plan carries a `jira_tickets:` list and the Agile rules are loaded, an advisory readiness checklist runs per ticket and never blocks. A design evidence packet, such as one from `mk:figma`, is cited and not re-analysed (`references/design-evidence-consumption.md`).

## Outputs

```
tasks/plans/YYMMDD-name/
  plan.md           overview, 80 lines at most
  research/         researcher reports (hard mode)
  phase-01-name.md  12-section detail, 150 lines at most
```

The skill never starts the next command. Type `/mk:cook <plan path>` yourself in a fresh session. With `tdd_mode` on, the printed cook command includes `--tdd`.

## Gotchas

Rewrite a goal that describes an activity ("Implement OAuth") as an outcome ("Users can log in with OAuth"). Every acceptance criterion needs a command or file check. Do not use `--deep` to choose an architecture, since deep maps a chosen approach. A failed integrity check after task hydration stops the run for a human to fix.
