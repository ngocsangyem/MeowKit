## What it does

`mk:ship` is Phase 5 (Ship), run by the `shipper` agent after review. Bare `/mk:ship` runs `prepare`: it inspects the selected changes, runs the scoped checks, shows the files proposed for staging and asks before it creates a local commit. It does not push, open a PR or touch issues or versions. `/mk:ship release` pushes the branch and creates or updates its PR. `/mk:ship publish` handles versions, the changelog and issues. Both need your explicit request.

Shipping needs no plan or review verdict and nothing blocks on a missing one. If a non-trivial change has no plan in `tasks/plans/`, the skill says so and continues if you want to ship anyway. The one enforced control is the ship check: the `pre-ship` hook runs lint on changed files, their related tests and a type-check on `git commit`, `git push`, `git merge` and `gh pr create|merge`, and refuses the command when one fails.

## When not to use it

To audit the code before it lands, use `mk:review`. Ship does not re-run the adversarial review. For container, pipeline or infrastructure changes, use `mk:devops`.

## Usage

| Argument | Effect |
|---|---|
| `prepare` or none | Inspect, check, then ask before staging and again before the local commit. |
| `release` | Push the approved branch and create or update its PR. |
| `publish` | Decide the version bump, changelog and issue actions with you. It never picks a bump or creates external records on its own. |
| `official` / `beta` | Choose the target release branch for `release` or `publish`. |
| `--skip-tests` | Skip the test step, only after you confirm current-session evidence is enough. |
| `--dry-run` | Show the actions without running them. |
| `--advice` | Optional supervision by the `athena` agent at four checkpoints (guide, rescue, review, recheck), at most 4 calls per stage. Its advice never grants permission to push, merge or publish. |

## Steps

1. Prepare: detect the base branch, run pre-flight checks, merge the base branch, run tests, audit test coverage and plan completion, and review readiness.
2. Review: apply the structural and design checks and resolve PR comments (`references/pre-landing-review.md`).
3. Release (on request): version and changelog steps, commit, push, create or edit the PR, then `mk:document-release` so documentation lands in the same PR.
4. Post-ship: check CI and write rollback steps into the PR body.

The skill stops on a base branch checkout, merge conflicts it cannot resolve, in-branch test failures, coverage below the target, or plan gaps. It asks you about critical review issues and about uncommitted files, and reports pre-existing test failures instead of accepting them.

## Output

A summary lists the scope, pre-flight, tests, coverage, review counts, whether a local commit, push or publish happened, and one deploy classification with a line of evidence: `deployed`, `PR-only` or `not-applicable`.

If the verdict names `jira_tickets`, the skill offers to post the verdict to Jira, move the ticket to Done and check the business acceptance criteria. Without that field it skips these offers.

## Gotchas

- In a monorepo, bump only the package being shipped, using per-package VERSION files.
- Check CI after the push. A green local run can still fail on another Node version or environment.
- The design check runs only on frontend diffs.
