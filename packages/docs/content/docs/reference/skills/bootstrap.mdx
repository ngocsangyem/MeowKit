`mk:bootstrap` runs the whole path for a new project: research, design, plan, scaffold, implement through `mk:cook`, then docs. It owns application code (`src/`, `tests/`, project config) and never touches `.claude/`, which `mewkit init` sets up. It runs only when you invoke it.

## When not to use it

| If you need | Use |
|---|---|
| A feature in a project that already has source | `mk:plan-creator` then `mk:cook` |
| Kit setup only | `mewkit init` |
| An unattended multi-hour build of a specified product | `mk:autobuild` |
| A single task on an existing project | `mk:cook` |

## Usage

```bash
mk:bootstrap [requirements]
mk:bootstrap [requirements] --full
mk:bootstrap [requirements] --fast
mk:bootstrap [requirements] --parallel
```

| Mode | Flag | Research | Design | Plan flag | Cook flag |
|---|---|---|---|---|---|
| Auto | none | 2 to 3 parallel researchers | UI/UX designer if frontend, you approve | `--auto` | `--auto` |
| Full | `--full` | 2 to 4 researchers, you approve the summary | UI/UX if frontend, you confirm each choice | `--hard` | interactive |
| Fast | `--fast` | 6 parallel researchers, no confirmation | Skipped | `--fast` | `--auto` |
| Parallel | `--parallel` | 2 researchers | UI/UX if frontend, you confirm | `--parallel` | `--parallel` |

Auto runs `git init` with an initial commit without asking. Full asks first. Fast ends with `git add -A && git commit -m "feat: bootstrap [project-name]"` and is not complete until that commit exists. In the other modes the last step asks whether to commit. `--parallel` writes a plan with a file-ownership matrix and dependency graph, and cook runs several developer agents.

## What it does

The first flag picks `references/workflow-full.md`, `workflow-fast.md`, `workflow-parallel.md` or `workflow-auto.md`, which list the steps for that mode.

1. Plan first: `mk:plan-creator` with the mode's flag produces the architecture, modules, file structure and acceptance criteria. Every bootstrap makes a plan before any source file. Full mode can also run `mk:plan-ceo-review` on it.
2. Scaffold from the plan, following `references/scaffolding-principles.md`. `scripts/detect-stack.sh` detects the stack and `scripts/validate-bootstrap.sh` checks the result.
3. Shared phases (`references/shared-phases.md`): implement with `mk:cook` using the mode's flag, generate `docs/` and the README with `mk:docs-init`, then print a final report.

## Scaffolding rules

- Config files first, then the entry point, then one module at a time. Every file compiles and none is empty.
- Print the proposed directory tree for confirmation, then generate config, entry point and core module, remaining modules, test scaffolds, and finally the README and `code-standards.md`. Check for compile errors between steps.
- Mirror `tests/` to `src/`. Stay flat until a level has 5 or more files.
- Never generate `.claude/`, real `.env` files (only `.env.example`), lock files, build output, or `.vscode/` and `.idea/` unless asked.
- The minimum scaffold is a source entry point, a matching test, a package manifest, a compiler config if needed, `.gitignore` and `README.md`, extended from `config.example.json` features (Docker, CI, database).
- Use the stack's naming convention. If the stack is unknown, ask before generating.

`validate-bootstrap.sh` checks that `src/` and `tests/` exist, that source files are not empty and that no `[TODO]`, `[PROJECT_NAME]` or `[PLACEHOLDER]` token remains. It prints `BOOTSTRAP_VALID` (exit 0) or `BOOTSTRAP_INCOMPLETE` (exit 1).

## Gotchas

- Scaffolding before planning, and duplicating `mewkit init` by generating `.claude/`, are the two main mistakes.
- Do not generate 20 or more files for a simple project. Ask about scope first.
- Generate a large stack progressively, not in one pass, and use `mk:docs-finder` for current framework patterns.
- Research is skipped only in `--fast`. For a project of fewer than 5 files, use `--fast`.
- Full list: `references/gotchas.md`.
