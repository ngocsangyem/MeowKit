## What it does

Acts like a human tester by driving `mk:agent-browser` and `mk:playwright-cli`. It has two uses. From a spec or URL it runs a manual QA pass and writes a pass or fail report with evidence. It can also turn that pass into Playwright `.spec.ts` files. It runs in Phase 4 (Review) for reports and Phase 3 (Build) for generated tests.

## When not to use

For a fix-and-verify cycle that edits source use `mk:qa`. For autonomous AI-driven flows use `mk:agent-browser`.

## Usage

```bash
/mk:qa-manual tasks/plans/260315-auth-flow.md --report
/mk:qa-manual tasks/plans/260315-checkout.md --generate
/mk:qa-manual https://app.example.com
/mk:qa-manual <spec>
```

`--report` writes a QA report and `--generate` writes Playwright code. With neither, the skill works out the use case from the spec.

| Action | Skill used |
|---|---|
| Click, fill, type, navigate | `mk:playwright-cli`, which also yields Playwright code |
| Screenshots | `mk:agent-browser` |
| Login, session, MFA | `mk:agent-browser` |
| Run a generated test | `scripts/run-playwright.sh` (`npx playwright test`) |

## Steps

Use case A, manual QA: load the spec, extract the flows, walk each flow, check the outcomes and report. Use case B, code generation: run A, record the interactions and write the spec (`references/qa-process.md`, templates in `references/output-templates.md`).

Generated tests go in `tests/e2e/{feature-name}/` with a `common/` folder holding `{featureName}Selectors.ts`, `{featureName}Assertions.ts` and `{featureName}Intercepts.ts`, and the spec in `tests/e2e/[flow-name].spec.ts`. The skill detects whether the project uses `data-testid`, `data-cy` or `data-test`, greps the source to confirm each locator exists, and falls back to `getByRole` with a warning comment when it does not. Locators are role-based (`getByRole`, `getByLabel`, `getByText`, `getByTestId`), never CSS selectors.

## Authentication

When the flow reaches a login page, MFA or a 401 or 403, the skill stops and shows the URL. You sign in yourself in the browser window, or give it a saved auth state file. Reply `done` once signed in, `skip` to mark the flow SKIPPED, or `abort` to end with a partial report. It never asks for a password in chat, guesses credentials, uses hardcoded ones, continues without your reply or stores credentials in a file.

## Failures

A page load timeout is retried twice and then reported. A missing element triggers a new snapshot and an alternate locator. A missing spec file prompts you for a path or URL. A failing Playwright run shows the error with a fix hint.

## Gotchas

Check that the deployed version matches what you expect before a run, because stale builds give misleading failures. Generated specs must read credentials from environment variables, never inline.
