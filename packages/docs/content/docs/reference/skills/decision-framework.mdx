`mk:decision-framework` turns expert judgment into a repeatable decision system for a recurring, high-stakes choice such as returns triage, billing exceptions, incident response, support routing or compliance decisions. Use it when someone asks "how should we handle X cases?" or wants a triage system. It runs in Phase 1 (Plan) and the result is a document that a developer can implement as logic.

## When not to use it

For a one-off trade-off debated between options, use `mk:party`.

## Usage

```bash
/mk:decision-framework returns processing
/mk:decision-framework customer support triage
/mk:decision-framework security incident response
```

The argument describes the decision domain. If the domain is unclear, the skill asks for three example cases and derives the taxonomy from them. If no domain expert is available, the output is flagged `needs-expert-input` and uncertain classifications are marked.

## What it does

| Step | Action | Reference |
|---|---|---|
| 1 | Identify the decision: what is decided, who decides, how often | |
| 2 | Build a taxonomy of mutually exclusive case types, 3 to 7 top-level buckets | `references/decision-tree-template.md` |
| 3 | Order decision rules Safety, then Compliance, then Economics, then Speed, and document why each sits where it does | |
| 4 | Define a scoring matrix of 3 to 5 factors with weights summing to 100 percent, calibrated on 3 historical cases | `references/weighted-scoring-guide.md` |
| 5 | Define 4 escalation levels (Expert, Manager, Director, VP), each with authority scope, timeline and trigger | `references/escalation-protocol-template.md` |
| 6 | Add communication templates for Routine, Significant and Crisis tone | `references/communication-patterns.md` |
| 7 | Document edge cases as situation, why the obvious approach fails, correct approach | `references/edge-case-discovery.md` |

Worked examples are in `references/examples/`: returns triage, billing operations and incident response.

## Output

One document with seven parts: domain summary, classification taxonomy, decision rules, scoring matrix with calibration notes, a 4-level escalation table, one communication template per tone, and an edge case playbook with short entries per known exception.

## Gotchas

- Keep the taxonomy granular. Do not merge case types that need different decision rules.
- Calibrate scoring weights on real cases. Safety and compliance rules override the score.
- Give escalation timelines in hours, not "soon".
- Edge cases are the most important cases to get right. Collect them by asking the team what surprised them, and review them quarterly or after a significant decision failure.
