`mk:arch` owns the lifecycle of architecture decision records (ADRs): numbering, file layout, status changes and impact checks against decisions already taken. The `architect` agent writes the decision text. Reach for it when a non-obvious architectural choice needs a durable record, or when you want to know which decisions still hold.

## When not to use it

| If you need | Use |
|---|---|
| Boundary refactors and finding shallow modules | `mk:improve-codebase-architecture` |
| A trade-off debated between options | `mk:party` |

## Usage

```bash
mk:arch new [title]
mk:arch list
mk:arch review [number]
mk:arch impact [change description]
```

| Mode | What it does | Output |
|---|---|---|
| `new` | Scans existing ADRs for the next number, gathers context (decision, constraints, options) and asks if any is unknown, has `architect` write Title, Status (Proposed), Context, Decision, Consequences and Alternatives Considered | `docs/architecture/adr/YYMMDD-title.md` and a printed summary for review |
| `list` | Prints one row per ADR with number, title and status, with superseding links resolved | A table |
| `review` | Checks whether the decision is still valid, the context changed, or new alternatives exist. Updates the status when warranted (Proposed to Accepted, Accepted to Deprecated or Superseded by #N) | The ADR with dated review notes |
| `impact` | Finds the components and boundaries a change touches, the ADRs that cover them, and whether each is consistent, extended or in conflict | Components, ADRs, risk level and a recommendation |

## Gotchas

- A review never rewrites the original Context or Decision text. The ADR records what was decided at the time.
- A conflict found by `impact` is reported as a conflict, not softened to "mostly aligned".
- A new ADR is Proposed until someone reviews it.
- A superseded ADR stays in the tree with its status changed.
