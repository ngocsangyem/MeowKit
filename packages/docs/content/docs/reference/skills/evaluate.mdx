## What it does

mk:evaluate runs a built artifact and grades it by behaviour. It composes a rubric preset with `mk:rubric`, boots the build if given a path, probes each criterion, captures evidence (screenshots, HTTP responses, CLI transcripts) and writes a PASS, WARN or FAIL verdict. It is owned by the `evaluator` agent and never edits source files.

## When to use it

Use it after a generator iteration, after the build phase and before shipping a frontend, fullstack or CLI product, or when asked to "grade the running app" or "verify against the spec". Skip it for a library with no runnable artifact.

| Need | Use instead |
|---|---|
| Structural audit of a diff or PR | `mk:review` |
| Static linting | `mk:lint-and-validate` |
| A simple fix | `mk:fix` |

## Usage

`/mk:evaluate <target-url-or-path> [flags]`

| Flag | Effect |
|---|---|
| `--rubric-preset` | `frontend-app`, `backend-api`, `cli-tool` or `fullstack-product`. Overrides the auto-detected preset. |
| `--max-criteria` | Caps the criteria count (default 15). |
| `--no-boot` | Skips the boot step. The target must be a URL. |

```bash
/mk:evaluate http://localhost:3000 --rubric-preset frontend-app
/mk:evaluate ./dist/app --rubric-preset cli-tool --max-criteria 10
/mk:evaluate http://localhost:3000 --no-boot
```

The target type is detected from the argument: a URL maps to `frontend-app` or `backend-api`, an executable to `cli-tool`, a project directory to `frontend-app` or `backend-api`, and a mixed product uses `fullstack-product` from a user-provided spec.

## Steps

The skill runs `workflow.md` one step file at a time.

1. Load rubrics: detect the target type, compose the preset, load the skeptic persona, parse a sprint contract if one exists, cap criteria at 15.
2. Boot the app: health check a URL, start a path target and poll up to 30 seconds, smoke test a CLI with `--help` or `--version`.
3. Probe each criterion with a technique from `references/active-verification-patterns.md` (`mk:agent-browser` or `mk:playwright-cli` for UI flows, curl and jq for APIs, exit codes for CLIs) and capture evidence.
4. Aggregate per rubric, compute the weighted score, write the verdict file and run `scripts/validate-verdict.sh`.
5. Write one-line fix guidance per FAIL or WARN finding, append it to the verdict file and clean up booted processes.

## Verdict

A rubric that reaches its `hard_fail_threshold` makes the overall verdict FAIL. Otherwise a weighted score of 0.85 or more is PASS, 0.65 or more is WARN, and lower is FAIL. The verdict frontmatter has `task`, `evaluator_run`, `rubric_preset`, `model`, `overall`, `weighted_score`, `hard_fail_triggered` and `iterations`.

`validate-verdict.sh` rejects a PASS with an empty evidence folder and converts it to FAIL. The `frontend-app` preset loads four rubrics: product-depth, functionality, design-quality and originality.

## Output

| Path | Content |
|---|---|
| `tasks/reviews/YYMMDD-{slug}-evalverdict.md` | Verdict with YAML frontmatter and per-rubric results |
| `tasks/reviews/YYMMDD-{slug}-evalverdict-evidence/` | Screenshots, HTTP captures, CLI transcripts |

The caller also gets PASS, WARN or FAIL, the verdict path and a feedback summary for the generator.

## Gotchas

- Do not grade source code. Reading `.tsx` files instead of driving the build is static review.
- Passing tests do not prove the endpoint works. Run the build.
- A skeptic persona is reloaded before each criterion because leniency drift is the main failure mode.
- Step 1 sets the slug in `MEOWKIT_EVAL_SLUG` and step 4 reuses it. A different slug breaks the evidence paths.
- More than 15 criteria are split into batches.
