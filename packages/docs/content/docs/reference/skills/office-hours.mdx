## What it does

Runs a YC-style office hours session on a new product, feature or side-project idea whose problem and value are unproven, and saves a design doc. It produces no code. The skill asks the questions that show whether the idea is worth building before any plan exists, and the design doc feeds `mk:plan-creator` and `mk:plan-ceo-review`.

## When not to use

To critique an existing plan use `mk:plan-ceo-review`. To compare technical approaches for a settled requirement use `mk:brainstorming`. A bare request to "brainstorm" is ambiguous, so the skill asks whether you want product validation or technical approaches.

## Usage

Run `/mk:office-hours` and describe the idea, for example "I have an idea for a developer tool that generates API docs from code comments. Is this worth building?". There are no arguments. The skill asks about your goal and picks a mode.

| Mode | For | Questions |
|---|---|---|
| Startup | Startups and intrapreneurship | Six forcing questions, one at a time, with pushback |
| Builder | Hackathons, open source, learning, side projects | Five generative questions in a collaborator tone |

The six startup questions cover demand evidence, the status quo, the specific person who needs it most, the narrowest wedge, what surprised you when watching users, and whether the product matters more or less in three years. Which ones are asked depends on product stage. If you push back twice the skill moves on to alternatives. If a builder mentions customers or revenue, it switches to Startup mode.

For a health check on an existing product, ask for Product Lens Modes (`references/product-lens-modes.md`): a Founder Review that scores Growth, Retention, Revenue, Moat and Urgency, or a User Journey Audit that maps friction and time to value.

## Steps

1. Gather context (codebase, earlier design docs, your goal) and pick the mode.
2. Run discovery questions.
3. Check the landscape using generalized category terms, never your specific idea, and challenge the premises. An optional second opinion comes from a fresh-context subagent.
4. Generate two or three alternatives: minimal, ideal and lateral. UI ideas get a rough wireframe sketch.
5. Synthesize founder signals and write the design doc. An adversarial subagent reviews it on five dimensions, with up to three fix rounds.
6. Close with a reflection and next-skill recommendations.

The skill does not write code, scaffold a project or call an implementation skill. The step files are in `references/`.

## Output

The design doc is saved beside its plan under `tasks/plans/<slug>/`. The startup template covers problem, demand evidence, status quo, target user, wedge, constraints, premises, approaches, recommendation, open questions, success criteria and the assignment. The builder template is shorter. A new session on the same topic can point to an earlier doc with a `Supersedes:` field. Nothing is written to memory.

## Gotchas

Do not discuss how to build before the problem statement is complete, and do not evaluate ideas before at least three alternatives exist.
