## What it does

mk:elicit takes an existing artifact and applies one named lens to it. It returns numbered findings with a severity of CRITICAL, IMPORTANT or INFORMATIONAL, and recommendations. When the target is a verdict, the analysis is appended to the verdict file as a supplementary section. It never overwrites the original and never changes a verdict.

## When to use it

Use it after a `/mk:review` verdict, after a plan is written, or after any agent output when you say "dig deeper", "what am I missing" or "challenge this". It needs an existing artifact. Usage: `/mk:elicit` (interactive) or `/mk:elicit pre-mortem on this plan`.

| Need | Use instead |
|---|---|
| The first review of a diff | `mk:review` |
| Open exploration with no artifact | `mk:brainstorming` |
| Stuck on an approach | `mk:problem-solving` |

## Methods

| Method | Question it asks | Suited to |
|---|---|---|
| Pre-mortem | Assume this shipped and failed. Why? | Risk discovery, failure modes |
| Inversion | What would make this maximally wrong? | Assumption testing, edge cases |
| Red Team | You are an attacker. How do you exploit this? | Security, adversarial thinking |
| Socratic | What evidence supports each claim? | Logic validation, gap detection |
| First Principles | Strip assumptions. What is fundamentally true? | Architecture, simplification |
| Constraint Removal | What if constraint X did not exist? | Scope exploration |
| Stakeholder Mapping | Who else is affected? | Impact analysis, requirements gaps |
| Analogical | What similar system solved this differently? | Alternative approaches |

Without a chosen method, the skill suggests one from context.

| Context | Suggested method |
|---|---|
| Review found security issues | Red Team |
| Review found low coverage | Pre-mortem |
| Plan has many assumptions | First Principles |
| Architecture decision | Inversion |
| Many stakeholders | Stakeholder Mapping |
| Unclear | Socratic |

## Steps

1. Read the artifact being re-examined (verdict file, plan file or conversation).
2. Show the methods and ask for one, or suggest one.
3. Apply the method.
4. Write the analysis: method, numbered findings with severity, recommendations.
5. Optionally repeat with another method.

After a review verdict, the reviewer may offer to run elicitation. A CRITICAL finding does not re-open the review. Run `mk:review` again to get a revised verdict.

## Output

```markdown
## Elicitation: [Method Name]
**Target:** [what was re-examined]
**Method:** [lens applied]

### Findings
1. **[CRITICAL]** [finding], [recommendation]

### Summary
[1-2 sentence synthesis]

### Action Required
- [ ] [action items, if any]
```

## Gotchas

- Order matters. Red Team then Socratic finds attacks and checks them with evidence. The reverse often drops the adversarial framing.
- Socratic questioning has no natural end. Set a depth, for example 3 levels or no new claims.
- Inversion works on yes or no decisions. For several options use Constraint Removal or Stakeholder Mapping.
- A pre-mortem needs a scoped target (the plan, the migration). A vague target gives a generic worry list.

The skill is analysis only. It does not replace the review, change a verdict, generate code or run on its own.
