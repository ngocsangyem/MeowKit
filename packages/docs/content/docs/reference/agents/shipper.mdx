The shipper takes reviewed code to a pull request. It never commits to `main` or `master` and never force-pushes to a shared branch.

It runs on `haiku`. Tools: `Read`, `Grep`, `Glob`, `Bash`. Per-runtime model pins are on [Agent models](/guide/agent-models).

## When to use

It runs in Phase 5 after review. It is not used for implementation. Its sequence includes the commit and PR that [git-manager](/reference/agents/git-manager) leaves out of its own scope.

## Ship sequence

1. Run the test suite, linter and type checker. All must pass.
2. Commit with a conventional prefix.
3. Create a feature branch and open a pull request.
4. Verify CI passes on the PR.
5. Document the rollback procedure.

For production changes it supports gradual rollout with monitoring checkpoints and rollback triggers.

The `pre-ship` hook runs its own ship check (lint on changed files, related tests, type-check) on `git commit`, `git push`, `git merge` and `gh pr create|merge`, independent of this agent.

It reads the passing review verdict at `tasks/reviews/YYMMDD-name-verdict.md`. It does not ship a change whose verdict has a FAIL dimension and raises it with you instead. That is a rule the agent follows, not a hook.

## Hand-offs and failures

- A shipped change (PR created, CI passing) goes to [documenter](/reference/agents/documenter). The hand-off lists the PR URL, branch, commit hash, rollback doc location, CI status and deploy applicability (`deployed`, `not-applicable` or `PR-only`).
- Failed pre-ship checks go back to [developer](/reference/agents/developer) or [tester](/reference/agents/tester), with the exact failing check.
- A failing CI is reported with log excerpts and routed back. It does not retry.
- If the PR cannot be created (no remote, auth failure) it commits and branches locally and asks you to push.

## What it does not do

It does not edit source, tests, plans or review files, skip rollback documentation or proceed past a failing CI.
