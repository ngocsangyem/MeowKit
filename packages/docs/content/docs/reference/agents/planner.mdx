The planner decides whether the task is worth building and how, then writes the plan with `mk:plan-creator`. It owns `tasks/plans/` and no other agent creates or edits plan files.

It runs on `opus`. Tools: `Read`, `Grep`, `Glob`, `Bash`, `Edit`, `Write`. Per-runtime model pins are on [Agent models](/guide/agent-models).

## When to use

It runs in Phase 1 for standard and complex tasks, before code is written. It is not used for implementation or review verdicts.

## What it does

- Applies the product lens (is this the right thing, or a symptom?) and the engineering lens (alternatives, trade-offs, existing patterns).
- Writes the plan through `mk:plan-creator` into `tasks/plans/YYMMDD-name/`: `plan.md` plus `phase-XX-name.md` files.
- Presents the plan so you can confirm or change it before the build. Nothing blocks an edit without an agreed plan, so this step is the planner's job.
- Estimates effort and flags risks. It sends unclear tasks back with specific questions, and states assumptions in the plan's Risk Flags when it cannot ask.
- Loads team memory on demand with `grep -rilE` over `.meowkit/memory/` and opens only matching entries.

## Planning modes

| Flag | Output |
|---|---|
| `--fast` | One `plan.md` with goal, context, scope, constraints, approach and acceptance criteria. No researchers. |
| `--hard` (default for complex work) | `plan.md` (80 lines or fewer) plus phase files. |
| `--deep` | Hard mode plus one scout per phase. Triggers on 5 or more directories or a complex refactor. Also writes `red-team-findings.md`. |
| `--parallel` | Two researchers on different aspects, merged before the plan is written. |
| `--two` | Two competing plans with an Approach Comparison. You pick one. |
| `--product-level` | A product spec for green-field builds (vision, features with user stories, design language, AI integration, out of scope). No phase files, file paths, class names or schemas. |

`--tdd` composes with these and adds test-first sections to each phase file. Subcommands are `red-team {path}`, `validate {path}` and `archive` on `/mk:plan-creator`.

## Beads

For a complex task touching 5 or more files, it splits the work into beads: atomic units, each with a name (`bead-NN-description`), file scope, binary acceptance criteria, a size of about 150 lines and dependencies. Beads fit one context window of about 70K tokens.

## Hand-offs

- Architectural decisions go to [architect](/reference/agents/architect).
- An implementation-ready plan goes to [developer](/reference/agents/developer). With TDD on, [tester](/reference/agents/tester) goes first.
- A `product-level` plan goes to `mk:autobuild`, not to the developer.
- Each hand-off includes the plan path, the recommended agent sequence and risk flags.

For an external URL that `mk:docs-finder` cannot cover it delegates to `mk:web-to-markdown` with `--wtm-accept-risk`.

## What it does not do

It writes no code, tests or config, and does not approve its own plans.
