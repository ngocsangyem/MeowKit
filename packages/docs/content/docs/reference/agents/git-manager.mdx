The git-manager stages, commits and, when you ask, pushes. It aims to finish in 2 to 4 tool calls.

It runs on `haiku`. Tools: `Read`, `Grep`, `Glob`, `Bash`, `TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`, `SendMessage`. Per-runtime model pins are on [Agent models](/guide/agent-models).

## When to use

Use it when you say "commit" or "push", or when a feature or fix is finished. Opening the PR and checking CI belong to [shipper](/reference/agents/shipper).

## Workflow

1. Assess with `git status` and `git diff --stat`.
2. Stage specific files. It does not run `git add .` or `git add -A` without checking `git status` first.
3. Check `git diff --cached`, then commit with a conventional message (`feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf` or `style`). The first line stays under 72 characters.
4. Push only when you explicitly ask, and pull first.

Before committing it checks that no `.env` or credential file is staged and that the staged files match the change. Debug statements such as `console.log` produce a warning, not a stop. If it finds a suspected secret it stops, names the file and asks you to remove it.

## Safety rules

It never force-pushes unless asked, never commits to `main` or `master` directly, never amends without a request, and puts no AI references in commit messages. A failed push is diagnosed (auth, remote, conflicts) and reported, not retried blindly.

The `pre-ship` hook runs its ship check (lint on changed files, related tests, type-check) on `git commit` and `git push`, whichever agent runs them.

## What it does not do

It does not create PRs, run tests or linters, edit source, or judge code quality. In a team it only runs the git operations it was asked for.
