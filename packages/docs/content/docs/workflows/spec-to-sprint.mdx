---
title: "Tickets to Sprint Planning"
description: "Research-driven workflow from ticket evaluation through codebase review to sprint planning."
---

This playbook evaluates tickets, checks them against the codebase and produces a planning report. You decide what the sprint commits to.

**Best for:** Tech leads, engineering managers, sprint planners
**Time estimate:** 5 to 15 minutes, depending on ticket count
**Skills used:** [mk:jira-evaluator](/reference/skills/jira-evaluator), [mk:jira-estimator](/reference/skills/jira-estimator), [mk:planning-engine](/reference/skills/planning-engine), [mk:jira-issue](/reference/skills/jira-issue), [mk:scout](/reference/skills/scout) (optional), [mk:confluence-spec-analyst](/reference/skills/confluence-spec-analyst) or [mk:web-to-markdown](/reference/skills/web-to-markdown) for a spec

<Callout title="Not for implementing a ticket" type="warn">

This playbook plans new work into a sprint. To implement an existing ticket, use [Ticket to Code](/workflows/ticket-to-code).

</Callout>

## Quick path

```bash
/mk:jira-evaluator AUTH-201                   # per ticket: ready?
/mk:jira-estimator AUTH-201                   # per ticket: how big?
/mk:planning-engine review AUTH-201 --scout   # check the estimate against the codebase
/mk:planning-engine plan --tickets AUTH-201,AUTH-202 --capacity 40
```

You end up with a sprint plan backed by codebase evidence as well as estimates. Every step produces a report that you read and decide on. Nothing creates tickets, assigns people or changes a sprint on its own.

Jira access needs the `jira-as` CLI and three variables in `.meowkit/.env`; see [Jira Integration](/guides/jira-integration).

## Step 1: Have tickets

The playbook assumes the work is already in Jira. If you start from a spec, import it first (next section) and create the tickets yourself.

### Importing a spec

Confluence:

1. `/mk:confluence-spec-analyst analyze <PAGE-ID>` writes a Spec Research Report: requirements, acceptance criteria, gaps and suggested stories. It is read-only.
2. Resolve the `[MISSING]`, `[VAGUE]` and `[AMBIGUOUS]` flags with the product manager, for example with `mk:confluence-collaborate` to leave a footer comment on the page.
3. Optionally scan feasibility with `/mk:scout` and `/mk:docs-finder` (see [step 3 of the walkthrough](/workflows/spec-to-pr-walkthrough/step-03-tech-feasibility)).
4. Create the tickets yourself (Step 2).
5. In Step 5, pass the report back with `--spec <report-path>`.

Notion or another URL: `/mk:web-to-markdown <spec-url>` converts the page, then `/mk:intake` on the markdown gives a similar report. Create tickets yourself.

[Spec to PR: Behind the Scenes](/workflows/spec-to-pr-walkthrough) shows every skill in this path in order.

## Step 2: Create tickets

For the stories you accept from the report:

```bash
/mk:jira-issue create --project AUTH --type Story --summary "Implement OAuth2 login" \
  --description "OAuth2 flow for Google and GitHub providers"
```

You choose which stories exist, their priority and their wording.

## Step 3: Evaluate and estimate

```bash
/mk:jira-evaluator AUTH-201
/mk:jira-estimator AUTH-201
```

You get a complexity assessment and a point suggestion. The team makes the final estimate in planning poker. [Ticket Evaluation](/workflows/ticket-evaluation) explains the output.

## Step 4: Tech review (optional)

```bash
/mk:scout
/mk:planning-engine review AUTH-201 --scout
```

The Tech Review Report lists affected files, a feasibility rating, dependencies, risks and complexity signals.

## Step 5: Plan the sprint

```bash
/mk:planning-engine plan --tickets AUTH-201,AUTH-202,AUTH-203 --capacity 40
```

With a spec report from Step 1:

```bash
/mk:planning-engine plan \
  --tickets AUTH-201,AUTH-202,AUTH-203 \
  --capacity 40 \
  --scout \
  --spec tasks/reports/spec-research-260511-q3-auth-refresh.md
```

The Planning Report has a sprint goal candidate, a dependency map, grouping suggestions and a capacity analysis. With `--spec` it adds a `## Spec Context (mk:confluence-spec-analyst)` section with the upstream requirements, acceptance criteria and gaps. The team then negotiates the sprint goal and commits. For sprint goals, amendments and close-out, see [Agile / Scrum](/workflows/agile-scrum).

## You can start at any step

| Starting point | Start at |
|---|---|
| Tickets ready | Step 3 |
| A spec or URL | "Importing a spec", then Step 2 |
| One ticket | Step 4 |
| Ready to plan the sprint | Step 5 |

No step needs the previous step's output.

## Who decides

| Decision | Who | What the tools give you |
|---|---|---|
| Which stories to create | You | Suggestions in the spec or intake report |
| Story point estimates | The team | Complexity signals |
| Which tickets enter the sprint | The team | Grouping suggestions |
| Sprint goal | Product owner and team | A candidate draft |
| Dependency resolution | The team | Cycle detection |
