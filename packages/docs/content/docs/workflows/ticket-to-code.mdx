You picked up a Jira ticket. This playbook goes from reading it to a PR and an updated ticket, one command per step.

**Best for:** Developers picking up tickets from the sprint backlog
**Time estimate:** Varies with the ticket
**Skills used:** [mk:jira-analyst](/reference/skills/jira-analyst), [mk:jira-evaluator](/reference/skills/jira-evaluator), [mk:jira-lifecycle](/reference/skills/jira-lifecycle), [mk:jira-collaborate](/reference/skills/jira-collaborate), [mk:jira-relationships](/reference/skills/jira-relationships), [mk:planning-engine](/reference/skills/planning-engine), [mk:scout](/reference/skills/scout), [mk:plan-creator](/reference/skills/plan-creator), [mk:cook](/reference/skills/cook), [mk:review](/reference/skills/review), [mk:ship](/reference/skills/ship)

## Quick path

```bash
/mk:jira-analyst AUTH-201                       # read the ticket and its attachments
/mk:jira-evaluator AUTH-201                     # is it ready to work on?
/mk:jira-lifecycle transition AUTH-201 --to "In Progress"
/mk:plan-creator implement OAuth2 login per AUTH-201   # plan, agree it with the agent
/mk:cook tasks/plans/<plan-dir>/plan.md         # build and review
/mk:ship                                        # prepare the commit; `/mk:ship release` opens the PR
```

You end up with a PR and a ticket moved to its next status. The phases behind `mk:cook` are explained on [Workflow](/core-concepts/workflow).

## Prerequisites

Jira access needs the `jira-as` CLI and three variables in `.meowkit/.env`. [Jira Integration](/guides/jira-integration) covers the install, the token and what to check when authentication fails.

## Step 1: Understand the ticket

```bash
/mk:jira-analyst AUTH-201      # description, acceptance criteria, comments, attachments, links
/mk:jira-evaluator AUTH-201    # complexity and gaps
/mk:jira-estimator AUTH-201    # story point suggestion
```

The evaluator flags `[MISSING]` and `[AMBIGUOUS]` items. If the ticket is unclear, ask the product owner before you continue. [Ticket Evaluation](/workflows/ticket-evaluation) explains the output. If the ticket has screenshots, video or a Figma link, see [Ticket with Media](/workflows/ticket-with-media).

## Step 2: Check the ticket against the code

```bash
/mk:scout
/mk:planning-engine review AUTH-201 --scout
```

The Tech Review Report lists affected files, a feasibility rating, dependencies and risks. `mk:planning-engine` asks you to run scout first when you pass `--scout`.

For a bug, run `/mk:investigate` and paste the ticket description and repro steps into the prompt. It works on your local codebase and does not read Jira.

## Step 3: Move the ticket to In Progress

```bash
/mk:jira-lifecycle transition AUTH-201 --to "In Progress"
```

`mk:jira-lifecycle` reads your project's workflow before it suggests transitions. If the ticket is already Done or Closed, check which transitions exist; you may need your team's reopen process.

## Step 4: Plan

```bash
/mk:plan-creator implement OAuth2 login per AUTH-201
```

The plan goes under `tasks/plans/YYMMDD-name/`. Read it and agree it before building. For a small, clear fix, skip the plan and run `/mk:fix` with the ticket text.

## Step 5: Implement and review

```bash
/mk:cook tasks/plans/<plan-dir>/plan.md
# or, for a quick job
/mk:cook "Implement OAuth2 login per AUTH-201" --fast

/mk:review
```

`mk:review` writes a verdict. Read it before you ship; no hook blocks shipping on it.

## Step 6: Ship

```bash
/mk:ship
```

By default `mk:ship` prepares the commit and asks before it stages or commits. `/mk:ship release` pushes the branch and opens the PR. On every `git commit`, `git push` and `gh pr create`, the ship check runs lint on the changed files, their related tests and a type-check, and refuses the command if one fails. See [Ship Safely](/guides/ship-safely).

## Step 7: Update the ticket

```bash
/mk:jira-lifecycle transition AUTH-201 --to "Done" --resolution Fixed
/mk:jira-collaborate add a comment to AUTH-201: "Implemented OAuth2 login. PR #42."
/mk:jira-relationships link AUTH-201 as relates-to AUTH-202
```

## Variations by ticket type

| Ticket | Command order |
|---|---|
| Bug | `mk:jira-analyst`, `mk:jira-evaluator`, transition, `mk:investigate` (paste repro steps), `mk:fix`, `mk:review`, `mk:ship`, transition to Done |
| Story | `mk:jira-analyst`, `mk:planning-engine review --scout`, transition, `mk:plan-creator`, `mk:cook`, `mk:review`, `mk:ship`, transition to Done |
| Technical task | `mk:jira-analyst`, transition, `mk:cook "..." --fast`, `mk:review`, `mk:ship`, transition to Done |

## When something goes wrong

| Situation | What to do |
|---|---|
| Acceptance criteria are vague | The evaluator flags `[MISSING]`. Ask the product owner. |
| The ticket is too large | The evaluator rates it Complex (8 to 13 points). Ask to split it. |
| Blocked by another ticket | Link it with `mk:jira-relationships` (`blocked-by`) and work on something else. |
| Harder than estimated | Run `mk:jira-estimator` again and share the result with the team. |
| Tests fail after implementing | `/mk:investigate`, then `/mk:fix`. |
| Review finds issues | Fix them, run `/mk:review` again, then `/mk:ship`. |

Other `mk:jira` leaves that help here: `mk:jira-search` (related issues by JQL), `mk:jira-time` (log work), `mk:jira-agile` (sprint and epic membership) and `mk:jira-dev` (branch names and PR descriptions). The [`mk:jira` reference](/reference/skills/jira) lists them all.
