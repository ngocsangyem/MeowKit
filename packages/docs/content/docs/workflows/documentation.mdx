This playbook keeps project documentation in step with the code.

**Best for:** Post-feature updates, new project setup, changelog polish
**Time estimate:** 10 to 20 minutes
**Skills used:** [mk:document-release](/reference/skills/document-release), [mk:docs-init](/reference/skills/docs-init), [mk:llms](/reference/skills/llms)
**Agents involved:** documenter

## Overview

The **documenter** agent owns `docs/`, except `docs/architecture/` (the architect's) and `docs/journal/` (the journal-writer's). It uses `mk:document-release` for updates after shipping, `mk:docs-init` for a first docs set and `mk:llms` for an `llms.txt` index.

## After shipping a feature

After a PR is created, `mk:ship` reports whether the diff seems to affect documentation and offers `/mk:document-release`. It does not run it by itself. To run it:

```bash
/mk:document-release
```

[mk:document-release](/reference/skills/document-release):

1. Reads the diff and changelog for what shipped.
2. Cross-references README, architecture, contributing and agent docs.
3. Applies clear factual updates directly and asks before narrative changes.
4. Polishes the CHANGELOG voice (imperative mood), without overwriting entries.
5. Cleans up TODOS: marks completed items and captures deferred work.

## Starting a new project

```bash
/mk:docs-init
```

[mk:docs-init](/reference/skills/docs-init) scans the codebase and generates the first docs set from what it finds, such as `README.md` and `docs/architecture/system-architecture.md`. A small project gets a README and a codebase summary only.

## Generating llms.txt

```bash
/mk:llms ./docs --url https://docs.example.com
```

[mk:llms](/reference/skills/llms) generates `llms.txt`, an index for AI tools that follows [llmstxt.org](https://llmstxt.org). `--full` also writes `llms-full.txt` with inline content, and `--output` sets the location. A Python script does the scanning, title extraction and categorizing, and Claude reviews the output.

## What the documenter does

| Does | Does not |
|---|---|
| Update `docs/` when code changes | Write in `docs/architecture/` (the architect owns it) |
| Generate changelogs from conventional commits | Write in `docs/journal/` (the journal-writer owns it) |
| Flag documentation gaps | Change source code or tests |
| Check docs against the implementation | Generate placeholder content |
