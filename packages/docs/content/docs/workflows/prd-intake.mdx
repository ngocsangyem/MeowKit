`mk:intake` analyses one ticket or PRD and returns a structured report. This page describes the pipeline and how to trigger it. The Jira leaves handle reading and writing the ticket.

**Best for:** Team leads, engineering managers, DevOps teams
**Time estimate:** About 2 minutes per ticket
**Skills used:** [mk:intake](/reference/skills/intake), [mk:jira-issue](/reference/skills/jira-issue), [mk:jira-evaluator](/reference/skills/jira-evaluator), [mk:jira-lifecycle](/reference/skills/jira-lifecycle), [mk:jira-relationships](/reference/skills/jira-relationships), [mk:jira-collaborate](/reference/skills/jira-collaborate), [mk:scale-routing](/reference/skills/scale-routing), [mk:scout](/reference/skills/scout), [mk:investigate](/reference/skills/investigate)

## Quick path

```bash
/mk:intake PRD-123          # classify area, score completeness, run RCA if it is a bug
/mk:jira-evaluator PRD-123  # readiness
/mk:jira-lifecycle transition PRD-123 --to "In Analysis"
```

You end up with a structured analysis, posted back to the ticket as a comment once you accept it. The analysis also works on pasted text, so you can try it before setting up Jira.

## Prerequisites

Jira access needs the `jira-as` CLI and three variables in `.meowkit/.env`; see [Jira Integration](/guides/jira-integration). Without them intake still runs on pasted text and skips the Jira steps. Linear (through its MCP server) and GitHub (through `gh`) work as sources too.

### Product areas (optional)

To map tickets to code paths and owners, create `.meowkit/product-areas.yaml`. `mk:scale-routing` reads it during classification:

```yaml
areas:
  - name: Authentication
    paths: ["src/auth/**", "src/middleware/auth*"]
    keywords: ["login", "session", "token", "OAuth", "JWT"]
    pic: ["alice", "bob"]

  - name: Payments
    paths: ["src/billing/**", "src/stripe/**"]
    keywords: ["payment", "invoice", "subscription", "charge"]
    pic: ["charlie"]
```

Without the file, classification uses keywords only and reports no owner.

### Triggers

- On demand: `/mk:intake PRD-123`.
- Automated: a Jira Automation rule (issue created, type PRD) sends a webhook to your service, which calls `claude -p "analyze ticket: <content>"`.

## What intake does

| Step | What happens |
|---|---|
| Receive | Reads the ticket through `mk:jira-issue` (or Linear, GitHub, a Confluence page or pasted text). |
| Sanitize | Checks the ticket text for injection patterns. A hit stops the run and reports the quote. |
| Media | Analyzes screenshots, video, Figma links and PDFs. See [Ticket with Media](/workflows/ticket-with-media). |
| Classify | `mk:scale-routing` matches the text against its domain table and `product-areas.yaml`. |
| Completeness | Scores the ticket out of 100 against eight dimensions (below). |
| Scan | `mk:scout` finds related files, components and patterns. |
| Root cause | For bugs, `mk:investigate` runs an RCA (5 Whys, Ishikawa or 8D by complexity). |
| Assess | Lists affected files, test gaps and implementation complexity. |
| Jira enrichment | When the `mk:jira-*` leaves are available, adds Jira metadata and suggests leaf actions. |
| Report and post | Builds the report and posts it through the source's adapter, for example `mk:jira-collaborate` for Jira. |

### Completeness score

| Dimension | Weight |
|---|---|
| Goal or problem statement | 20 |
| Acceptance criteria | 20 |
| Scope (in and out) | 15 |
| Steps to reproduce (bugs) | 15 |
| Technical constraints | 10 |
| Priority or severity | 10 |
| Dependencies | 10 |
| Design or visual (UI tasks) | 10 |

A missing dimension subtracts its weight from 100. For backend-only tasks the design weight moves to goal and acceptance criteria. A score of 80 or more is ready, 60 to 79 needs minor clarification, 40 to 59 should be clarified before work starts, and below 40 goes back to the author.

### The report

```markdown
## Intake Analysis: PRD-123
### Product Area: Authentication (confidence: HIGH)
### Completeness: 55/100
Missing: acceptance criteria, steps to reproduce, out-of-scope section
### Technical Considerations
- Session timeout hardcoded at 24h (src/config/auth.ts:15)
- Token refresh only triggers on navigation
### Root Cause (bugs only)
Token refresh is tied to navigation events, so idle users get no refresh.
### Suggested Breakdown
1. Add a background refresh interval (src/auth/session-manager.ts)
2. Support sliding expiration in the session config
3. Add an integration test for an idle session
### Related Tickets
- PRD-098 (similar scope), BUG-045 (possibly the same cause)
### Suggested PIC
alice (Authentication owner)
```

Root cause appears for bugs only. Feature PRDs get the completeness score and a breakdown.

## Acting on the report

Intake suggests transitions, links and an owner. You run them:

```bash
/mk:jira-lifecycle transition PRD-123 --to "In Analysis"
/mk:jira-relationships link PRD-123 as blocks BUG-045
/mk:jira-lifecycle assign PRD-123 to alice
```

For readiness and size, continue with [Ticket Evaluation](/workflows/ticket-evaluation). When the ticket is ready, a feature goes to `mk:cook` and a bug to `mk:fix` (see [Ticket to Code](/workflows/ticket-to-code)); a security concern goes to `mk:cso`.

## What intake does not do

- Manage your team roster. You maintain `product-areas.yaml`.
- Balance workload. It reports open ticket counts per owner, and your rules decide assignment.
- Enforce Jira workflow rules. It suggests transitions and your Jira automation enforces them.
- Deduplicate exactly. It finds related tickets by keyword; exact duplicates are a JQL job.

## Gotchas

- Without the three `MEOW_JIRA_*` variables there is no Jira reading or writing. Pasted text still works.
- A stale `product-areas.yaml` gives wrong classification. Update it when the team changes.
- The owner suggestion is a suggestion. Confirm it before assigning.
- If a webhook runs intake on every ticket, filter by type and project to stay inside rate limits.
