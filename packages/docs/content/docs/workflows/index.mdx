A workflow is an end-to-end playbook for a scenario that has its own starting material. If you just want to build, fix, review, or ship something, you want a [guide](/guides/build-a-feature) instead — those are shorter and there is one per task.

## Start from what you have

| What is in front of you | What you want out of it | Playbook |
|---|---|---|
| A Jira ticket | A merged PR | [Ticket to Code](/workflows/ticket-to-code) |
| A Jira ticket | To know whether it is ready to work on, and how big | [Ticket Evaluation](/workflows/ticket-evaluation) |
| A ticket with screenshots, video, or a Figma link | Implementation that matches the design | [Ticket with Media](/workflows/ticket-with-media) |
| A Confluence spec | A planned sprint | [Spec to Sprint](/workflows/spec-to-sprint) |
| A Confluence spec | A merged PR, with every step explained | [Spec to PR: Behind the Scenes](/workflows/spec-to-pr-walkthrough) |
| A PRD or a pile of incoming requests | Analysed, triaged, estimated work | [PRD Intake](/workflows/prd-intake) |
| A sprint and a team | Sprint goal, DoR/DoD, retro actions, spike governance | [Agile / Scrum](/workflows/agile-scrum) |
| Commit history | A retrospective people will read | [Sprint Retrospective](/workflows/retrospective) |
| An empty directory | A working MeowKit project | [Starting a New Project](/workflows/new-project) |
| Somebody else's undocumented codebase | Enough understanding to change it safely | [Maintaining Old Projects](/workflows/maintenance) |

If the input to your task is "the code I already have", you are almost certainly looking for a guide rather than a workflow.
