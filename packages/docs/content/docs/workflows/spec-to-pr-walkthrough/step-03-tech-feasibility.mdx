---
title: "Step 3: Tech feasibility breakdown"
description: "A read-only scan with mk:scout and mk:docs-finder that shows whether the spec needs a refactor first or already exists in the codebase, before anything is filed and estimated."
---

Before tickets exist, check the spec against the codebase. The aim is to find "this needs a refactor first" or "we already shipped this" before the team commits to an estimate.

Two skills run at this point. `mk:scout` maps the codebase and `mk:docs-finder` fetches current third-party docs. `mk:planning-engine` is the deeper tech-review skill, and it needs Jira ticket keys, so per-ticket review happens in [Step 7](/workflows/spec-to-pr-walkthrough/step-07-tech-review). No skill reads a Spec Research Report and lists impacted files without ticket keys, so the comparison in this step is yours.

## Prompt

```bash
/mk:scout authentication oauth session
# Read the Spec Research Report next to the scout output. Then:
/mk:docs-finder "Google OAuth 2.0 current scopes and PKCE requirements"
```

## What happens

| Action | Skill |
| --- | --- |
| Splits the repository into segments and searches them with parallel Explore subagents. The report has an architecture fingerprint, key directories, relevant files, patterns, a complexity estimate and a handoff note. | `mk:scout` |
| Looks up current docs for any third-party API or library the spec names, using Context7 and Context Hub. | `mk:docs-finder` |
| You read the report's `Suggested User Stories` section next to the scout output and decide whether each story is feasible as written, needs splitting, or hits a missing prerequisite. | You |

Scout does not save its report by default. It writes `.meowkit/cache/codebase-map.md` only when you ask it to, and it keeps just the fingerprint and key directories. Step 7 uses the scout output still in your session, or asks you to run scout again.

## Example decisions

After reading the report against the scout output, you might record something like this:

| Spec story | Feasibility | Decision |
| --- | --- | --- |
| "Sign in with Google" | High: an OAuth provider plugin pattern exists, so this adds a provider | Create the ticket as written |
| "Sliding 24h session" | Medium: the middleware exists but uses a fixed expiry and needs a refactor | Create the ticket and flag the dependency on "Sign in with Google" |
| "OAuth users can add password later" | Low: the users table has no OAuth provider column | Defer to a later sprint and raise it with the PM |

## What you carry forward

Keep a short note per suggested story with its feasibility level and any structural prerequisite. Put it in the Spec Research Report or in a follow-up Confluence comment. It feeds [Step 4](/workflows/spec-to-pr-walkthrough/step-04-create-tickets) and is checked again in Step 7.
