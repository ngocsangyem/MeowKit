This walkthrough follows one spec through Confluence, Jira and your codebase. Each step page shows the prompt you type, the skills that run, the artifact written and the decision that is yours. It is written for developers who want to know why the workflow has this shape and not only which commands to run.

A first read takes about 20 minutes. A real run takes one to four hours, depending on ticket size. For the commands only, [Ticket to Code](/workflows/ticket-to-code) covers the second half.

## Before you start

Jira access needs the `jira-as` CLI and three variables in `.meowkit/.env`. [Jira Integration](/guides/jira-integration) covers the install, the token and what to check when authentication fails. Confluence uses the same token and setup. [Confluence Integration](/guides/confluence-integration) covers the Cloud-only limit if you are on Server or Data Center.

The quick path, one command per stage:

```bash
/mk:confluence-spec-analyst analyze 12345 --include-children 1
/mk:jira-issue create --project AUTH --type Story ...   # one per story it found
/mk:planning-engine plan --tickets AUTH-201,AUTH-202 --capacity 40
/mk:cook AUTH-201                                       # then repeat per ticket
/mk:ship
```

## How the steps connect

Every skill writes an artifact, and you read it before the next step. The paths below mark where each one lands.

```mermaid
flowchart TD
    A["Step 1: spec report<br/>tasks/reports/"] --> B{"Step 2: gaps?"}
    B -->|yes| C["Footer comment to the PM"]
    C --> A
    B -->|no| D["Step 3 and 3.5: feasibility and sizing"]
    D --> E["Step 4 to 6: tickets, epic, estimates"]
    E --> F["Step 7: tech review and planning report<br/>tasks/reports/"]
    F --> G["Step 8: plans<br/>tasks/plans/&lt;slug&gt;/"]
    G --> H["Step 9: /mk:cook &lt;plan-path&gt;"]
    E -.->|"trivial ticket"| H
    H --> I["PR opened, review verdict in tasks/reviews/"]
    I --> J["Step 10: ticket Done, footer comment on the spec"]
```

A trivial ticket skips Steps 7 and 8. You hand cook a task description, and cook writes and agrees the plan in its own Phase 1.

Planning and review are practices in this workflow. You agree each plan and read each review verdict, and no hook blocks an edit or a commit when you skip either. The one enforced control is the [ship check](/core-concepts/enforcement#the-ship-check), which runs at commit, push, merge and PR.

Reports from Steps 1 to 7 stay in `tasks/reports/`, and plans from Step 8 go to `tasks/plans/<slug>/`. Nothing copies one into the other.

## What crosses between systems

```mermaid
flowchart LR
    CONF["Confluence<br/>spec page, footer comments"]
    JIRA["Jira<br/>tickets"]
    CODE["Codebase and Git<br/>branch, PR"]

    CONF -->|"spec URL in the ticket description"| JIRA
    JIRA -->|"ticket keys, branch names"| CODE
    CODE -.->|"PR body names the ticket"| JIRA
    JIRA -.->|"open questions (footer comment)"| CONF
    CODE -.->|"ship summary (footer comment)"| CONF
```

Solid arrows carry work forward. Dashed arrows write back to a system you already used.

## Decisions that are yours

| Decision | When |
| --- | --- |
| Which spec gaps to resolve before ticketing | After Step 1 |
| Feasibility, and which stories to defer | After Step 3 |
| Which stories to file, and whether to batch-create | After Step 3.5 |
| Ranking and dependencies | Step 5 |
| Story-point estimate | After Step 6, as a team |
| Plan mode per ticket, and agreeing each plan | Step 8, or cook's Phase 1 for trivial tickets |
| Whether to ship with WARN dimensions | After the Phase 4 verdict |

## When the situation differs

| Situation | What to do |
| --- | --- |
| The spec is already a Jira ticket | Start at Step 6. |
| Tickets exist but nobody analyzed a spec | Start at Step 6 and ask the product owner to fill in acceptance criteria. |
| The work is a bug | Use [Fix a Bug](/guides/fix-a-bug). The spec analyst does not apply. |
| A one-shot hotfix with no blast radius | `/mk:fix` skips the separate plan, as `scale-adaptive-rules.md` Rule 4 describes. |
| A green-field product | Use [Autonomous Build](/guides/autonomous-build) with `/mk:autobuild`. |
| The spec changed mid-sprint | Run `/mk:confluence-spec-analyst` again. The report ends with a page hash, which shows whether the page changed. |
| An estimate was far off | Update the points through `mk:jira-agile` and raise it at the retro. |
| A plan is more than 14 days old | Cook warns about it. Run `mk:plan-creator` again before cooking. |
| The review verdict is FAIL | Fix the failing dimension and run `/mk:review` again before shipping. |
