The PM has replied. You now know the Google scopes are `email` and `profile`, expiry is a sliding 24h window, and OAuth users can add a password later as a separate ticket. The Step 3.5 report has a size per story, so pass the one you choose with `--story-points`. Alternatively, `/mk:story-sizer --paste --auto-create --project AUTH` creates the tickets after one confirmation.

## Prompt

```bash
/mk:jira-issue create --project AUTH --type Story \
  --summary "Sign in with Google OAuth" \
  --story-points 3 \
  --description "Per spec page 12345 §R1. Scopes: email, profile.

  AC:
  - AC1. 'Sign in with Google' button redirects to Google consent
  - AC2. After consent, user lands on /dashboard with session cookie
  - AC3. Session uses sliding 24h expiry

  Spec: https://acme.atlassian.net/wiki/spaces/ENG/pages/12345"

/mk:jira-issue create --project AUTH --type Story \
  --summary "Sliding 24h session expiry"
  # ...

/mk:jira-issue create --project AUTH --type Task \
  --summary "Preserve email/password login flow (no-op test)"
  # ...
```

## What happens

| Layer | Action |
| --- | --- |
| Custom fields | If the project has required custom fields, `mk:jira-fields` finds them so you can fill them in. |
| Create | `mk:jira-issue` forks to the `jira-issue` agent, which creates one issue through the `jira-as` wrapper. |
| Result | Each created issue prints its key and URL. |
| Spec link | The description carries the Confluence URL as written. Nothing else syncs the spec and the tickets. |

`mk:jira-issue` handles one issue per call. The Spec Research Report offers `--with-commands`, which lists suggested `mk:jira-issue create` commands. You still run them yourself, so each ticket gets a read-through before it reaches a backlog.
