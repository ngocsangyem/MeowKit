You picked AUTH-201 for this sprint. Time to build.

## Prompt

```bash
# AUTH-201 has a plan from Step 8. Pass the plan path ("code mode").
# Cook skips its own Phase 1 and builds from the plan you agreed.
/mk:cook tasks/plans/260511-auth-201-google-oauth/plan.md

# AUTH-203 is trivial and skipped Step 8. Pass a task description.
# Cook runs Phase 1 itself and you agree the plan there.
/mk:cook implement AUTH-203
```

Useful flags: `--tdd` (failing tests first), `--fast` (skip research, still plan), `--auto` (run without pausing), `--verify` (light browser check) and `--strict` (full evaluator).

| Entry | Phase 1 |
| --- | --- |
| Plan path (AUTH-201, AUTH-202) | Skipped. Cook loads the plan from Step 8. |
| Task description (AUTH-203) | Cook runs `mk:plan-creator` for the task and you agree the plan before Phase 2. |

Nothing blocks Phase 3 when the plan is missing. Writing the plan and agreeing it first is the workflow. Cook skips it only when you say so and Phase 0 found no risk flags, and it notes the skip in the run summary.

## Phases

### Phase 0: Orient

`mk:agent-detector` runs first. It confirms the six always-on rules in `.claude/rules/`, loads `docs/project-context.md` when it exists, and classifies the task. `mk:scale-routing` matches the task against its domain table. The `risk-checklist` reference marks flags such as `AUTH` for login, session and OAuth terms. Cook then states the tier as `Task complexity: [TRIVIAL|STANDARD|COMPLEX] → [model]`.

Any flag in `AUTH`, `AUTHZ`, `DATA_MODEL`, `AUDIT_SEC` or `EXT_SYSTEM` forces the COMPLEX tier regardless of how small the task looks (`model-selection-rules.md`, Rule 2). AUTH-201 is a login feature, so it is COMPLEX. If scale-routing returns `level=high`, cook also turns on `--strict` unless you pass `--no-strict`.

### Phase 1: Plan

Skipped in code mode. Otherwise cook runs `mk:scout` and `mk:plan-creator`, then asks you to agree the plan (`Looks right`, `Revise plan` or `Abort`).

### Phase 2: Test

Optional by default. With `--tdd` or `MEOWKIT_TDD=1`, the `tester` agent writes failing tests for each acceptance criterion first, and Phase 3 starts only after they run and fail.

### Phase 3: Build

The `developer` agent works through the plan's phase files, runs type checks after each file change and retries up to three times with different approaches when tests fail. After three failures it calls `mk:investigate` for a root-cause report. After three more it stops and reports to you.

### Phase 3.5 and 3.6: Simplify and verify

`mk:simplify` reduces complexity once tests pass. `mk:verify` then runs build, lint, type-check, tests and coverage, scoped to the changed files. Both run before review.

### Phase 4: Review

`mk:review` runs the `reviewer` agent and writes `tasks/reviews/YYMMDD-name-verdict.md`. The verdict grades five dimensions:

| Dimension | What it covers |
| --- | --- |
| Correctness | Bugs against the acceptance criteria |
| Maintainability | Readability and conventions |
| Performance | Regressions |
| Security | Findings in the diff |
| Coverage | Whether every AC is implemented and tested |

Each is PASS, WARN or FAIL. Any FAIL makes the overall verdict FAIL, and a mix of PASS and WARN gives WARN.

You read the verdict before shipping. A FAIL is advice to fix that dimension and review again, and a WARN means you decide whether to ship as is or fix it first. No hook blocks the commit on the verdict. The ship check at commit time still runs lint, related tests and type-check.

### Phase 5: Ship

Cook stops after the verdict. A PASS is not a request to ship. When you ask, the `shipper` agent runs the pre-ship checks, commits with a conventional message, opens a PR and notes how to roll back.

`mk:jira-dev` produces the Jira-aware pieces. It only generates artifacts, and you run the resulting `git` and `gh` commands. Ask it for a branch name such as `feature/AUTH-201-google-oauth` and for a PR body that references the ticket. `mk:jira-lifecycle` then moves the ticket, for example to "In Review". Check your project's status names first, because `mk:jira-lifecycle` reads them from the discovered workflow in `tasks/jira-workflows/`.

On commit, push and `gh pr create`, the `pre-ship` hook runs lint on changed files, related tests and a type-check, and refuses the command when one fails. This is the one enforced control. See [the ship check](/core-concepts/enforcement#the-ship-check).

### Phase 6: Reflect

Cook runs this on an explicit close request, not automatically. It syncs the plan's checkboxes, evaluates docs impact with the `documenter` agent, and archives the plan with `mewkit plan archive` when every phase is done. `mk:memory` adds an entry only when the lesson cannot be read from the code, so most runs add nothing. Entries go in with `mewkit note decisions` or `mewkit note gotchas`, with the entry on stdin, in this shape:

```md
## First OAuth provider shipped without a token-refresh test  <!-- 2026-05-14 -->
Why: the reviewer caught it; the happy path passed without it
Apply when: adding any OAuth provider
Source: tasks/reviews/260514-auth-201-verdict.md
```
