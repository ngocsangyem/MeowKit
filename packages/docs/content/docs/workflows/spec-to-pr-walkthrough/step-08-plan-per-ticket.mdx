---
title: "Step 8: Plan per ticket with /mk:plan-creator"
description: "Running mk:plan-creator on its own before coding lets the team agree each plan at sprint kickoff instead of inside each developer's cook run. The mode follows the ticket's size and risk."
---

With a tech review for each ticket, run `mk:plan-creator` once per ticket. It writes a file-based plan that you read and agree with before any code is generated. The tech lead can then read every plan at sprint kickoff.

## Why run it before /mk:cook

`mk:cook` runs `mk:plan-creator` itself in Phase 1. Running it first has three effects:

1. You find problems such as a missing security review or a hidden migration at plan time, which costs minutes. Finding them at review costs the code that was generated.
2. Plans in `tasks/plans/` can be read side by side.
3. A plan file survives a lost session. A Phase 1 plan inside cook belongs to that one run.

Planning is a practice here. No hook blocks an edit or a commit when a plan is missing, so the agreement is something you do, and the plan file is the record.

`mk:cook` also accepts a plan path. In that "code mode" it skips Phase 1 and starts from the plan you agreed.

## Choosing the mode

| Ticket | Plan-creator mode |
| --- | --- |
| Trivial: rename, typo, single-file config | Skip this step. Plan-creator exits on trivial scope and points to `/mk:fix`. Cook can run the ticket from a task description. |
| Standard: a feature under about 5 files, a bug fix, an API endpoint | `--fast`: no research, `plan.md` only |
| Complex: auth, payments, data model, or any risk flag raised at Phase 0 | `--hard`: two researchers, `plan.md` plus phase files, a red-team pass and a validation interview |

Plan-creator also picks a mode from the scope itself in its first step (TRIVIAL exits, STANDARD runs fast, COMPLEX runs hard), and the flag overrides that choice. The `mk:agent-detector` risk flags work the same way. AUTH, AUTHZ, AUDIT_SEC and EXT_SYSTEM force the COMPLEX tier. DATA_MODEL and PUBLIC_CONTRACT force `mk:plan-creator --hard`. See [Step 9](/workflows/spec-to-pr-walkthrough/step-09-implement-with-cook) for Phase 0.

## Prompt

```bash
# AUTH-201 touches auth, so use the full pipeline
/mk:plan-creator --hard
# Give it the Tech Review Report path and the spec report path:
#   tasks/reports/<tech-review-report>.md
#   tasks/reports/confluence-spec-260511-0108-q3-auth-refresh.md

# AUTH-202 is a standard ticket
/mk:plan-creator --fast

# AUTH-203 is trivial: skip this step and give the task to /mk:cook in Step 9
```

## What happens

| Layer | Action |
| --- | --- |
| Scope check | The first step reads team memory for matching entries, picks a workflow model (feature, bugfix, refactor or security) and sets the planning mode. |
| Intake packet | If you pass two or more existing artifacts, such as the Tech Review Report and the spec report, plan-creator merges them into one intake packet at `research/plan-intake-packet.md` in the plan folder. With fewer than two paths, nothing changes. |
| Research | With `--hard`, two researchers run in parallel, each limited to 5 tool calls, and write to `tasks/plans/<slug>/research/`. |
| Definition of Ready | If the plan frontmatter has `jira_tickets:` and the Agile rules are loaded, plan-creator renders a Definition of Ready checklist. It is advisory and does not block. |
| Plan files | `tasks/plans/YYMMDD-<slug>/plan.md` (overview, at most 80 lines) and, outside `--fast`, a `phase-XX-*.md` file per phase. |
| Presenting the plan | Plan-creator shows the plan with a self-check of what was done, skipped and uncertain. You agree it or ask for changes. |

## What you have after Step 8

```
tasks/
├── reports/                                     from Steps 1, 6 and 7, left where they were written
│   ├── confluence-spec-260511-0108-q3-auth-refresh.md
│   ├── jira-evaluate-260511-0930-AUTH-201.md
│   └── ...                                      Tech Review and Planning Reports
└── plans/
    ├── 260511-auth-201-google-oauth/            --hard
    │   ├── plan.md
    │   ├── phase-01-service-skeleton.md
    │   ├── phase-02-controller-route.md
    │   └── research/                            researcher reports and the intake packet
    └── 260511-auth-202-sliding-session/         --fast
        └── plan.md
```

AUTH-203 has no plan folder. It is trivial and is handled in Step 9.

The reports from Steps 1 to 7 stay in `tasks/reports/`. Plan-creator does not copy them into the plan folder, but a report path given at invocation is read through the intake packet.

## Staleness

`mk:cook` warns when a plan is more than 14 days old, because the codebase may have changed. For a sprint that slips, run `mk:plan-creator` again on the stale tickets before cook. No hook checks that you re-read a plan, so re-read it when you pick up the ticket, especially before `/mk:cook --auto`.
