description: "With ticket keys in hand, mk:planning-engine reviews each ticket and plans the sprint. --spec brings the Confluence analysis into the planning report."
---

Step 3 could only scan the codebase. Now that tickets exist, `mk:planning-engine` has the keys it needs and runs in two modes.

| Mode | Command | Output |
| --- | --- | --- |
| Per-ticket review | `mk:planning-engine review AUTH-201 --scout` | Tech Review Report for one ticket |
| Sprint plan with spec context | `mk:planning-engine plan --tickets AUTH-201,AUTH-202,AUTH-203 --capacity 40 --scout --spec <report-path>` | Planning Report: sprint goal candidate, dependency map, grouping, sequencing, capacity analysis and a `## Spec Context (mk:confluence-spec-analyst)` section |

`review` also accepts `--graph` for third-party code graph context. The skill does not create tickets, assign work, set points or move tickets into sprints.

## Prompt

```bash
# Per ticket: run for each ticket entering the sprint
/mk:scout                                            # skip if the Step 3 output is still in this session
/mk:planning-engine review AUTH-201 --scout

# Sprint level: ties the spec to the planning view
/mk:planning-engine plan \
  --tickets AUTH-201,AUTH-202,AUTH-203 \
  --capacity 40 \
  --scout \
  --spec tasks/reports/confluence-spec-260511-0108-q3-auth-refresh.md
```

## What happens

| Piece | Action |
| --- | --- |
| Scout | Skills cannot call each other, so `--scout` uses scout output already in the session. If there is none, planning-engine asks you to run `/mk:scout` and exits. Without scout the report carries `[NO_CODEBASE_CONTEXT]`. |
| `review` | Reads the ticket through `mk:jira-issue` (or `mk:jira-search`) and passes it, with the scout output, to the `tech-analyzer` agent. Ticket text is treated as data. |
| `plan --spec` | Checks that the path exists and that the first line starts with `# Spec Research Report:`. If not, it asks you to run `mk:confluence-spec-analyst` first and exits. It never runs that skill itself. It then extracts Requirements, Acceptance Criteria and Gaps and passes them to the `planning-reporter` agent. |
| Failures | A read error after validation adds `[NO_SPEC_CONTEXT: <error>]` to the report, and planning continues without spec context. Capacity analysis shows `[INCOMPLETE]` when more than 30% of tickets have no estimate. |
| Where reports go | The active plan's `research/` folder if one exists, otherwise `tasks/reports/`. At this point no plan exists, so they land in `tasks/reports/`. Step 8 does not move them. |

Ticket evaluation and estimation from [Step 6](/workflows/spec-to-pr-walkthrough/step-06-refine-and-estimate) improve the review and enable capacity analysis. Without them the review does its own lighter assessment and the planner skips capacity.

## Tech Review Report sections

The template has these sections: Ticket Summary, Codebase Context, Feasibility Assessment (rating Straightforward, Complex or Needs Spike, plus confidence), What, Why, How, Dependencies, Risks, Complexity Signals and Open Questions. The complexity signals are observations for the team and not an estimate.

An abridged example:

```markdown
# Tech Review: AUTH-201

## Codebase Context
- Affected files: src/auth/oauth.controller.ts, src/auth/session.middleware.ts, src/auth/auth.module.ts

## Feasibility Assessment
**Rating:** Straightforward
**Confidence:** High

## Dependencies
- Blocked by: AUTH-202 (sliding session must land first; current middleware uses a fixed 24h expiry)
- External: Google OAuth 2.0

## Risks
- Google's PKCE requirement changed; verify against current Google docs
```
