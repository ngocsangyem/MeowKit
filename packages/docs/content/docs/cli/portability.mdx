title: "Portability"
description: "Install MeowKit for Codex or Cursor, keep those installs current, and see what each tool supports."

MeowKit is authored for Claude Code. The `.claude/` tree is the one authored copy of the kit. Codex, Cursor, Grok, Pi and OMP each get the files they read, projected from that tree plus a small overlay for the runtime's hooks and config. You install a runtime with `mewkit init --target`.

## Install for another runtime

```bash
mewkit init --target codex
mewkit init --target cursor
mewkit init --target grok
mewkit init --target pi
mewkit init --target omp
```

`--target` skips the toolkit picker and creates the runtimes you name. Each install writes the runtime's skills, agents, always-on text and hooks, plus `AGENTS.md` where the runtime reads it.

| Runtime | What the install writes |
| --- | --- |
| Codex | `AGENTS.md`, agents as `.codex/agents/*.toml`, skills under `.agents/skills/`, hooks in `.codex/hooks.json`, and `.codex/config.toml` |
| Cursor | `AGENTS.md`, agents as `.cursor/agents/*.md`, skills under `.cursor/skills/`, rules as `.cursor/rules/*.mdc`, and hooks in `.cursor/hooks.json` |
| Grok | Skills under `.grok/skills/`, the hook file `.grok/hooks/meowkit.json` with its helpers under `.grok/meowkit/`, and `AGENTS.md` |
| Pi | Skills under `.agents/skills/`, one extension `.pi/extensions/meowkit.ts`, and `AGENTS.md` |
| OMP | Skills under `.agents/skills/`, agents as `.omp/agents/*.md`, the hook module `.omp/hooks/pre/meowkit.ts`, and `AGENTS.md` |

Codex, Pi and OMP read the same `.agents/skills/` folder. When more than one of them is installed, they all get the same runtime-neutral skill text there. Alone, each gets its own invocation form: Codex calls a skill as `$mk-x`, and Pi and OMP as `/skill:mk-x`.

Grok, Pi and OMP install into a project only. `--global` covers Claude Code, Codex and Cursor. A `--target` install does not need a `.claude/` directory. Cursor also accepts `--mcp-profiles <name>` to merge MCP profiles into `.cursor/mcp.json`. Applying a profile to a repository with a git remote also needs `--allow-cloud-mcp`.

`--dry-run` prints what would be written without writing it.

## Keep an install current

`mewkit upgrade` refreshes each installed runtime from the ledger that its install wrote. If the project also has `.claude/`, the upgrade updates that too, so the installs move together.

Adding or removing a runtime with `init` or `uninstall` re-plans the runtimes already installed whose files depend on the set. Adding a runtime and then removing it leaves the same tree as a fresh install of the runtimes that stay.

Some projects still carry a `.cursor/` or `.codex/` directory from the retired `migrate` command. Those directories have no ledger. `upgrade` leaves them alone and prints a notice. To switch to the projected install, run:

```bash
mewkit init --target cursor    # or: mewkit init --target codex
```

## Legacy memory

No runtime install imports the memory store that older releases kept under `.claude/`. If you still need content from it, copy the parts you need into `.meowkit/memory/`.

## What each tool supports

The table shows what each runtime's install writes. ✓ included · — not included.

| Tool | Agents | Skills | Rules | Hooks | Config |
| --- | :---: | :---: | :---: | :---: | :---: |
| Codex | ✓ | ✓ | `AGENTS.md` | ✓ | ✓ |
| Cursor | ✓ | ✓ | ✓ | ✓ | MCP profiles |
| Grok | — | ✓ | `AGENTS.md` | ✓ | — |
| Pi | — | ✓ | `AGENTS.md` | ✓ | — |
| OMP | ✓ | ✓ | `AGENTS.md` | ✓ | — |

**Notes:**

- The installs ship the kit's own agents, skills and hooks. Your custom agents, commands and hooks in `.claude/` are not projected. Port them by hand.
- Codex agents are written as TOML and each pins a model by its tier. Change a pin by editing the agent file or through a Codex config profile.
- Grok documents no file format for agents, so the kit writes none. Pi has no subagents, so it has no agents either.
- Grok and Pi load project hooks only after the project is trusted: `/hooks-trust` or a start with `--trust` for Grok, `/trust` for Pi. OMP has no trust step. The [enforcement matrix](https://github.com/ngocsangyem/MeowKit/blob/main/docs/core/enforcement-matrix.md) lists what each runtime enforces. The Grok, Pi and OMP entries have not yet been run in a live session.

## providers

Show provider support (level, role, surfaces). Pass a provider name to see one. With `--lifecycle`, show the capability-adapter view instead: the four support levels, repo-context acquisition tools, storage boundary, and the per-lifecycle-event matrix (which events a provider fires and which it can actually gate/deny on).

```bash
mewkit providers [<provider>] [--json]
mewkit providers --lifecycle              # event × provider matrix (proven-gate markers)
mewkit providers <provider> --lifecycle   # one provider: levels, acquisition, lifecycle, evidence
```

| Flag          | Description                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| `--lifecycle` | Capability-adapter view: support levels + acquisition + lifecycle-event support. A `gate` is claimed only where a runtime hook can deny/block (never for version-gated or observe-only events). |
| `--json`      | Machine-readable output.                                                                                      |

Per-provider output also reports `--advice` supervision support. The harness and the direct
strategy consult are tracked as **separate capabilities**: a runtime can expose one and not
the other, so one proving out says nothing about the other. Each carries a state
(`supported`, `degraded`, `unverified`, `unavailable`), what the state rests on, and what
would move it up a rung.

Structural evidence never produces a `supported` claim: the files existing is not the same
as a runtime having done the thing. A capability leaves `unverified` only from a recorded
live run. Codex additionally reports its mutation ban as `degraded (behavioral)`, because a
Codex agent definition carries no per-agent tool field to enforce one. Claude Code and
Cursor enforce theirs structurally.

## pack

Manage optional capability packs layered over the base kit.

```bash
mewkit pack list [--json]
mewkit pack add <pack>… [--yes] [--beta]
mewkit pack remove <pack>…
```
