These commands change or inspect the shape of the project: installing the kit, configuring it, checking it, and moving it to a newer kit. Which runtime gets which files is under [Runtimes and scopes](/cli#runtimes-and-scopes).

`init`, `upgrade` and `uninstall` all take `--json` (print one JSON document), `--force` (replace or remove files you edited) and `--global` (act on your home directory). With no terminal to confirm in (CI, a pipe, a hook), `init --force` and `upgrade --force` only show their plan and exit 3 unless you also pass `--yes`. Before any of them changes anything, it copies every file it is about to change or remove into a new directory under `.meowkit/backups/` (`~/.mewkit/state/backups/` globally). `mewkit backups list` shows those copies and `mewkit backups restore <id>` puts one back; `--dry-run` on `restore` prints the plan and changes nothing.

## init

```bash
mewkit init                                   # picker for the runtimes
mewkit init --target claude-code,cursor
mewkit init --target grok,pi,omp
mewkit init --target claude-code --delivery plugin
mewkit init --global --target all
mewkit init --target codex --dry-run
```

`init` downloads the newest kit release and checks it against the release's `checksums.txt` and its `kit-contract.json`. It then writes the kit for each runtime. `--beta` allows a prerelease and `--kit-version v2.16.0` pins one release. `--offline` uses the newest kit already in the cache. `--kit-archive <zip>` installs a local `meowkit-release.zip`, checked against `--kit-sha256` or a `checksums.txt` beside it. `--allow-unverified-kit` accepts a kit with no checksum or no `kit-contract.json`; leave it off unless you built the kit yourself.

`--target` takes `claude-code`, `codex`, `cursor`, `grok`, `pi`, `omp`, a comma-separated list of them, or `all`. Without `--target`, a terminal shows a picker with Claude Code preselected. With no terminal, `--yes` or an existing `.claude/` means Claude Code, and otherwise the command exits 2 and names `--target`. An unrecognized `--target` is refused by name.

Grok, Pi and OMP install at project scope only, so `--global` covers Claude Code, Codex and Cursor. The Grok, Pi and OMP guards follow the vendors' documentation and have not been run in a live session ([Enforcement & Security](/core-concepts/enforcement) page).

| Flag | Runtime | Effect |
| --- | --- | --- |
| `--profile <name>` | Claude Code | Install a subset: `core`, `developer`, `product`, `atlassian`, `security`, `research`, `full`. Running `init` again with a narrower profile removes what it no longer includes, unless you edited it |
| `--delivery native\|plugin` | Claude Code | The on-disk shape: the host's own directory, or the same content plus a plugin manifest. Refused with the other runtimes |
| `--skill-packs <packs>` | Every runtime except Claude Code | Comma-separated skill packs, or `all`. Omitted installs every skill; an empty value installs the default pack only |
| `--mcp-profiles <names\|all>` | Cursor | Merge MCP servers into `.cursor/mcp.json`; your own servers win. A project with a git remote also needs `--allow-cloud-mcp` |

For Claude Code at project scope, `init` also writes the committed launcher `.meowkit/bin/mewkit` and the `.claude/runtime.json` that points the hooks at it ([how hooks reach mewkit](/cli#how-hooks-reach-mewkit)). In the MeowKit source repository itself, `init` refuses unless you pass `--allow-kit-source`, because `.claude/` there is the kit's authored source.

### Taking over an npm install

If the retired npm `mewkit` CLI installed a runtime in this project, `init --target <runtime>` adopts it. The npm CLI's install record becomes the starting ownership index and kit files are refreshed. Files the kit no longer ships are removed when they still match what the record says was installed, and files you edited are kept. Adoption works at project scope only, and only when you ask for it with `init`. `upgrade` never adopts: on a runtime with an npm install record and no ownership index, it names the `init` command to run. [Moving from the npm CLI](/migration/from-npx-mewkit) walks through it.

### An install whose record is gone

The ownership index in `.meowkit/state/ownership/` records which files the kit wrote. The kit's `.meowkit/.gitignore` leaves that folder out of the ignore list, so commit it: a clone then knows what the kit installed. Kit 3.0.0 and earlier ignored it, so a clone of a project installed from one of them has the kit's files and no record.

`init` handles that case from the kit release the files came from. A Claude Code install names its release in `.claude/kit-contract.json`; for any other runtime, name it with `--adopt-from <tag>`. A file that still holds what that release installed is taken as the kit's, so `init` updates it or removes it when the new kit dropped it. A file that differs is yours and is kept. Hook registrations that release added are recorded too, so one that points at a removed script is taken out.

When `init` finds 20 or more kit paths holding other contents and cannot get the release to compare them with, it writes nothing and says so. Run it again with `--adopt-from <tag>`, or with `--force` to replace the files, each one backed up first. A release before 3.0.0 also needs `--allow-unverified-kit`.

## upgrade

```bash
mewkit upgrade
mewkit upgrade --target cursor --dry-run
mewkit upgrade --check
mewkit upgrade --list
```

`upgrade` moves the runtimes installed here to the newest kit, with the packs they were installed with. It takes the same kit-source flags as `init`. A file you edited after the kit wrote it is kept and named, and the command exits 6; `--force` replaces it. `--check` compares each installed runtime with the newest release (`--beta` for the prerelease channel) and `--list` shows the recent releases. Neither changes anything, and with `--offline` both read the kits in the cache instead of GitHub. `upgrade` removes a file the new kit dropped only when it still holds what the installed kit wrote there, so it needs that kit. It reads it from the cache, and downloads the release again when the cache has lost it (a clone, another machine). With `--offline`, `--kit-archive` or an install that did not come from a published release, it downloads nothing, keeps the dropped files and says so. `--no-cleanup` is accepted for scripts written for the npm CLI and does nothing, because a downloaded kit always stays in the cache.

## uninstall

```bash
mewkit uninstall            # shows what would go
mewkit uninstall --yes
mewkit uninstall --global --target codex --yes
```

`uninstall` removes exactly what the kit installed: owned files, merged hook handlers, blocks and keys. Your own content in shared files stays. An edited file is kept unless you pass `--force`.

## setup

`setup` runs guided post-install configuration. Each step is idempotent.

```bash
mewkit setup              # run all steps
mewkit setup --only=env   # run one step
```

| Step | What it does |
| --- | --- |
| `skill-envs` | Prepares the per-skill Python environments under `.meowkit/envs/<skill>/` |
| `mcp` | Copies `mcp.json.example` to `.mcp.json` |
| `env` | Creates `.meowkit/.env` for your API keys |
| `gitignore` | Appends MeowKit entries to `.gitignore` |
| `project-context` | Prints the `/mk:project-context` command to run in your first session (it writes `docs/project-context.md`) |

`--system-deps` installs missing system-level dependencies, and `--yes` answers its prompt when there is no terminal. `--skills <list>` names the skills whose interpreter environments to create, and `--dry-run` prints what would happen without writing. `mewkit skill --list` shows every skill that declares a runtime and the state of its environment; `mewkit skill env <skill>` creates or repairs one.

## doctor

```bash
mewkit doctor
mewkit doctor --global --json
mewkit doctor provenance --explain
mewkit doctor --hard-gates
```

Without flags `doctor` changes nothing. It checks Node.js (the kit's hooks need 24 or later), the installs at both scopes (owned files present or edited), that every kit hook script a hook file names exists, Codex project trust, and which kit hook behaviours a runtime does not carry. It exits 1 when a check fails.

| Flag | Effect |
| --- | --- |
| `--report` | Append a shareable report block |
| `--providers` | Add what each runtime's adapter can enforce |
| `--state` | Add the state taxonomy |
| `--hard-gates` | Run the kit's privacy block, injection scan and ship check in a scratch project and report which ones block |
| `--explain` | With `provenance`: name the files behind each count |
| `--adopt` | Rebuild the npm CLI's ownership baseline (`.meowkit/metadata.json`) from the local kit cache, or refuse |
| `--target`, `--global`, `--json` | Narrow to some runtimes, check your home directory, print JSON |

`mewkit doctor provenance` classifies each installed file against the install baseline and says what local evidence can and cannot prove.

### Rows about shared hosts and weakened checks

With more than one runtime or toolkit installed, `doctor` also reports where they overlap. These rows are `ok` or `warn` and change no exit code, except `kit copies: unrecorded`, which fails.

| Row | Reports |
| --- | --- |
| `coexistence: cross-runtime load` | An installed runtime loads the kit's skills, agents or hooks from more than one root in this project, because it also reads another installed runtime's tree. Cursor, for one, also loads `.claude/` and `.agents/skills`. The row lists each second root with the vendor setting that stops the load, where one is documented |
| `kit copies: unrecorded` | A copy of a kit skill or agent that no install here recorded sits under a second root an installed runtime reads, for example `.pi/skills/mk-cook` beside `.agents/skills/mk-cook`. It loads beside the installed one and no upgrade or uninstall removes it. Delete what the row lists |
| `coexistence: agent names`, `foreign hooks`, `instruction files`, `skill listing` | The same agent name at project and home scope, a hook this install does not own on an event it also uses, another always-on instruction source, or a combined skill listing large enough that a host may drop descriptions |
| `checks: weakened` | An observer is switched off in a config file, `MEOWKIT_HOOK_PROFILE=fast` or the Cursor kill switch is set, or a host setting stops kit hooks from running. The privacy block and the ship check cannot be switched off by config |
| `guards: integrity` | An installed guard file no longer matches the bytes recorded at install, or a hook registration names a file that is not there |

The coexistence rows read names, sizes and hook executable names outside the project. They never read a file's body beyond its frontmatter, never read an environment value, and never follow a symlink inside a scanned tree. `doctor` reads files, not hosts: it cannot tell your host's version, whether Codex has trusted a changed hook, or whether a session started in a directory with no `.claude/`.

## providers

```bash
mewkit providers --target codex
mewkit providers --lifecycle
mewkit providers codex --lifecycle
```

`providers` shows what each runtime would get from the kit at this scope (files, skills, hooks and gaps) without installing anything. `providers <runtime>` is the same as `--target <runtime>`. `--lifecycle` shows instead which lifecycle events each runtime fires and which of them can block. With one runtime it adds support levels, invocation shapes and enforcement gaps. [Portability](/cli/portability#providers) has more.

## validate

`validate` checks the structure and wiring of a project's `.claude/`. It does not check that the guards block; `doctor --hard-gates` does that.

```bash
mewkit validate
mewkit validate --target codex .
```

With no flag it runs the full sweep. In the MeowKit authoring checkout the sweep also reports provider-specific wording in generic skill bodies as advisory portability WARNs. A focused run takes one of these flags:

| Flag | Runs only |
| --- | --- |
| `--workflow` | The `workflow.yaml` drift check |
| `--ownership` | The artifact ownership-completeness check |
| `--agents` | The declared agent-contract conformance checks |
| `--substrate` | The responsibility-substrate drift and untagged check |
| `--packs` | The pack-manifest coherence and safety check |
| `--rules` | The routing-table-breadth check |
| `--capabilities` | The capability-manifest checks |
| `--memory` | The committed team-memory store lint |
| `--frontmatter` | The `SKILL.md` frontmatter schema and runtime-contract check |
| `--docs-refs` | The `.claude` to `docs/*` reference allowlist check |

`--portable` adds the portable provider-contract checks to the full sweep. `--strict` treats WARN as failure (exit 1). `--mode <mode>` is a maintainer override of the detected consumer profile.

`--target <codex|cursor|grok|pi|omp> [dir]` validates a generated runtime install instead of a `.claude/` project. The directory defaults to the current one. It is read-only and cannot be combined with `--portable`.

## versions

```bash
mewkit versions
mewkit versions --offline
```

`versions` lists the kits installed here, the kits in the cache, the kits available on GitHub (`--beta` includes prereleases, `--offline` skips GitHub), and the kit contract range this binary supports.

## self-update

```bash
mewkit self-update --check
mewkit self-update
mewkit self-update --channel beta
```

`self-update` fetches the newest binary release's `binary-manifest.json`, refuses an older version, checks the archive's SHA-256 and size, and replaces the running binary. The previous binary stays beside it with an `.old` suffix. `--check` only reports, and exits 3 when an update exists. `init` makes the same comparison against the newest stable release and, when this binary is older, ends with one line on stderr naming it; it is skipped with `--offline`, `--kit-archive` or `--kit-dir`, and stays silent when GitHub does not answer within 2 seconds. When the running version has been withdrawn, it says so.
